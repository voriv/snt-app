# REQ-INFRA-CICD-001: CI/CD пайплайн на GitHub Actions

> **Статус:** Реализовано (2026-08-06)
> **Задача:** B-013 «CI/CD пайплайн (GitHub Actions)», эпик INFRA, приоритет medium
> **Масштаб:** tech-debt / medium — lint, type-check, unit, integration, component, e2e (main), сборка Docker (main)

## 1. Бизнес-контекст и Цель

Приложение СНТ «Берёзки-НТ» разработано на стеке Next.js 15 + TypeScript + PostgreSQL + Prisma + Playwright и включает несколько видов тестирования (unit, integration, component, e2e). В текущем состоянии отсутствует формализованное требование на CI/CD-пайплайн, хотя базовый workflow `.github/workflows/ci.yml` уже существует. Необходима формализация требований к автоматизированному пайплайну для обеспечения качества кода при каждом пуше в основную ветку и каждого pull request.

- **Бизнес-цель:** Автоматизировать проверки качества кода (lint, typecheck, тесты, сборка) при каждом пуше в `main` и каждом PR, чтобы предотвратить попадание сломанного кода в основную ветку и ускорить обратную связь для разработчиков.
- **Стейкхолдеры / Пользователи:** Разработчики (получают быстрый фидбэк), QA-инженеры (гарантия выполнения тестов), Team Lead / Tech Lead (контроль качества), DevOps (настройка и поддержка пайплайна).

### Область действия (Scope)
- **Scope-01:** В границы B-013 входят этапы lint, type-check, unit, integration, component, e2e-тесты и сборка/публикация Docker-образа при пуше в `main`.
- **Scope-02:** Деплой на сервер (staging/production) **НЕ входит** в B-013 — он покрыт отдельным workflow [`deploy-ssh.yml`](../../.github/workflows/deploy-ssh.yml) (задача вне скоупа). Действие CI/CD «CI/CD Pipeline» не включает этап деплоя.
- **Scope-03:** Данный REQ формализует требования к уже существующему workflow [`ci.yml`](../../.github/workflows/ci.yml), а не создаёт новый с нуля.

## 2. Бизнес-правила и Логика (Business Rules)

- **BR-01:** Каждый pull request в ветку `main` должен пройти все проверки CI (lint, typecheck, unit-тесты, интеграционные тесты, компонентные тесты) перед слиянием.
- **BR-02:** Пуш в ветку `main` должен запускать полный пайплайн, включающий все проверки BR-01 плюс E2E-тесты и сборку Docker-образа.
- **BR-03:** Пуш в ветку `develop` должен запускать пайплайн качества (lint, typecheck, unit, integration, component), но не должен запускать E2E-тесты и Docker-сборку.
- **BR-04:** При падении любого этапа CI пайплайн должен остановиться и не переходить к следующим этапам, которые зависят от упавшего (fail-fast).
- **BR-05:** Зависимости всегда устанавливаются через `npm ci` (а не `npm install`) для детерминированной установки из `package-lock.json`.
- **BR-06:** Prisma Client должен быть сгенерирован (`npm run db:generate`) перед запуском любых тестов, требующих доступ к базе данных.
- **BR-07:** Схема базы данных должна быть применена (`prisma db push`) перед запуском интеграционных и E2E тестов.
- **BR-08:** Секреты (DOCKER_USERNAME, DOCKER_PASSWORD, SSH_HOST и др.) должны храниться в GitHub Secrets и не должны попадать в логи.
- **BR-09:** E2E-тесты должны выполняться с `forbidOnly=true` в CI-режиме, чтобы предотвратить случайный запуск только одного теста.
- **BR-10:** При провале E2E-теста в CI должен быть выполнен автоматический повтор (retry) не более 2 раз.
- **BR-11:** Артефакты тестов (скриншоты, видео, отчёты) должны сохраняться и быть доступны для скачивания после завершения пайплайна.

## 3. Функциональные требования

### 3.1 Триггеры пайплайна

- **FR-01:** Пайплайн должен запускаться автоматически при пуше в ветки `main` и `develop`.
- **FR-02:** Пайплайн должен запускаться автоматически при создании и обновлении pull request в ветку `main`.
- **FR-03:** Должна поддерживаться возможность ручного запуска пайплайна через `workflow_dispatch`.

### 3.2 Этап Lint и Type Check

- **FR-04:** Пайплайн должен выполнять `npm run lint` (ESLint) для проверки стиля кода.
- **FR-05:** Пайплайн должен выполнять `npm run type-check` (`tsc --noEmit`) для проверки типов TypeScript.
- **FR-06:** Этап lint/typecheck должен выполняться параллельно с другими независимыми этапами (не блокировать запуск тестов).

### 3.3 Этап Unit-тесты

- **FR-07:** Пайплайн должен выполнять `npm run test:unit` (Vitest) для запуска unit-тестов.
- **FR-08:** Перед запуском unit-тестов должен быть выполнен `npm run db:generate` для генерации Prisma Client.
- **FR-09:** Unit-тесты не требуют запущенной базы данных и должны выполняться в изоляции.

### 3.4 Этап Интеграционные тесты

- **FR-10:** Пайплайн должен выполнять `npm run test:integration` для запуска интеграционных тестов.
- **FR-11:** Для интеграционных тестов должна быть запущена сервис-база PostgreSQL (через GitHub Actions services) с параметрами: `POSTGRES_USER=test`, `POSTGRES_PASSWORD=test`, `POSTGRES_DB=snt_test`.
- **FR-12:** Перед запуском интеграционных тестов должна быть применена схема БД (`prisma db push`) с `DATABASE_URL=postgresql://test:test@localhost:5432/snt_test`.

### 3.5 Этап Компонентные тесты

- **FR-13:** Пайплайн должен выполнять `npm run test:components` для запуска компонентных тестов React.
- **FR-14:** Компонентные тесты не требуют запущенной базы данных.

### 3.6 Этап E2E-тесты

- **FR-15:** Пайплайн должен выполнять `npm run test:e2e` (Playwright) для запуска end-to-end тестов.
- **FR-16:** Для E2E-тестов должна быть запущена сервис-база PostgreSQL с теми же параметрами, что и для интеграционных тестов.
- **FR-17:** Перед запуском E2E-тестов должно быть выполнено: `npm run db:generate`, `prisma db push`, `npm run build`, `npm start`.
- **FR-18:** E2E-тесты должны запускаться с переменными окружения: `DATABASE_URL`, `NEXTAUTH_SECRET`, `NEXTAUTH_URL`, `ENABLE_TEST_ROUTES=true`.
- **FR-19:** Playwright должен быть установлен с зависимостями системы (`npx playwright install --with-deps`).
- **FR-20:** E2E-тесты должны выполняться только при пуше в `main` (не на PR и не на `develop`).

### 3.7 Этап Сборка Docker-образа

- **FR-21:** Пайплайн должен собирать Docker-образ приложения после успешного прохождения всех тестов.
- **FR-22:** Docker-образ должен быть запушен в Docker Hub с тегами: commit SHA и `latest` (для ветки `main`).
- **FR-23:** Должен использоваться GitHub Actions Cache для Docker-слоёв (`type=gha`).
- **FR-24:** Docker-сборка должна выполняться только при пуше в `main`.

### 3.8 Окружение и кэширование

- **FR-25:** Пайплайн должен использовать Node.js версии 24 (установлено в `env.NODE_VERSION`).
- **FR-26:** Должно быть настроено кэширование `npm` через `actions/setup-node@v4` с `cache: 'npm'`.
- **FR-27:** Переменные окружения `NODE_VERSION` и `POSTGRES_VERSION` должны быть определены на уровне workflow.

### 3.9 Артефакты и отчётность

- **FR-28:** Результаты E2E-тестов (скриншоты, видео, отчёты) должны быть сохранены как артефакт GitHub Actions.
- **FR-29:** При падении пайплайна должна быть видна конкретная причина (неуспешный шаг, ошибка, лог).

## 4. Нефункциональные требования (NFR) и Ограничения

- **NFR-01 (Время выполнения):** Полный пайплайн на пуше в `main` не должен превышать 15 минут от старта до финиша.
- **NFR-02 (Параллелизм):** Независимые этапы (lint, unit-tests, integration-tests, component-tests) должны выполняться параллельно для минимизации общего времени.
- **NFR-03 (Конкурирующие запуски):** При быстром следовании нескольких пушей в одну ветку, предыдущие запуски должны быть отменены (`concurrency` группировка по ветке).
- **NFR-04 (Безопасность секретов):** Секреты (DOCKER_USERNAME, DOCKER_PASSWORD, SSH_PRIVATE_KEY и др.) не должны выводиться в логи ни при каких условиях.
- **NFR-05 (Детерминизм):** Использование `npm ci` гарантирует, что установка зависимостей идентична локальному окружению разработчика.
- **NFR-06 (Платформа):** Пайплайн выполняется на runner `ubuntu-latest`.
- **NFR-07 (Ресурсы):** E2E-тесты используют не более 2 параллельных воркеров (`workers: 2` в Playwright конфиге).
- **NFR-08 (Таймауты):** Каждый шаг пайплайна должен иметь разумный таймаут (по умолчанию GitHub Actions предоставляет 6 часов на джобу).
- **NFR-09 (Версионирование actions):** Все используемые GitHub Actions должны быть зафиксированы по версии (например, `actions/checkout@v4`), а не по `main`.
- **NFR-10 (Поддерживаемость):** Структура workflow-файла должна быть документирована комментариями для каждого этапа.

## 5. Исключения и Граничные кейсы (Edge Cases)

- **EC-01:** Если Docker Hub недоступен при сборке образа, пайплайн должен завершиться ошибкой на этапе `build-docker`, но предыдущие этапы (тесты) должны иметь зелёный статус.
- **EC-01a:** Деплой на сервер не входит в B-013: этап `deploy-staging` из CI-пайплайна не реализуется и не блокирует сборку образа (деплой выполняется отдельным workflow `deploy-ssh.yml`).
- **EC-02:** Если E2E-тест нестабилен (flake), он должен быть автоматически повторён до 2 раз (`retries: 2` в Playwright конфиге при `CI=true`).
- **EC-03:** Если секреты Docker Hub не настроены в репозитории, этап `build-docker` должен быть пропущен (skip), а не провален.
- **EC-04:** Если приложение не запускается в течение 30 секунд после `npm start`, этап E2E-тестов должен завершиться с понятной ошибкой.
- **EC-05:** Если `package-lock.json` не совпадает с `package.json`, команда `npm ci` должна завершиться ошибкой (защита от ручного редактирования lock-файла).
- **EC-06:** При параллельных пушах в `main`, ранее запущенный пайплайн должен быть отменён, чтобы избежать расхождения артефактов.
- **EC-07:** Если база данных PostgreSQL не запускается (service health check fail), интеграционные и E2E тесты должны завершиться с ошибкой подключения, а не таймаутом.
- **EC-08:** При запуске E2E в CI (`CI=true`) Playwright не должен стартовать встроенный `webServer` (`npm run dev` из [`playwright.config.ts`](../../playwright.config.ts)), т.к. приложение запускается отдельным шагом `npm start`; использование `dev`-сервера в CI недопустимо.
- **EC-09:** Внутри [`playwright.config.ts`](../../playwright.config.ts) `webServer.env.DATABASE_URL` указывает порт `5433`, а в CI сервис-база поднят на порту `5432`. При запуске E2E в CI переменная `DATABASE_URL=postgresql://test:test@localhost:5432/snt_test` должна передаваться из шага пайплайна и переопределять значение из конфига, иначе тесты подключатся к несуществующей базе.

## 5a. Масштаб и ограничения (tech-debt / medium)

- **MS-01:** Многоэтапные запуски (nanoservices, matrix по Node-версиям, параллельный e2e на нескольких браузерах с отдельными сервисами) НЕ требуются для B-013. Достаточно единого набора джоб, соответствуя типу tech-debt / medium.
- **MS-02:** Скрипты запуска тестов фиксируются строго по [`package.json`](../../package.json): `test:unit`, `test:integration`, `test:components`, `test:e2e`. Скрипт `test:api` существует, но в состав B-013 не включается (уже покрыт конфигом; уточняется при реализации планировщиком).

## 6. Критерии приёмки

### AC-01: Пайплайн запускается при пуше в main
- **Given** разработчик сделал `git push origin main`,
- **When** срабатывает триггер GitHub Actions,
- **Then** запускается workflow `CI/CD Pipeline` и выполняются все 6 этапов (lint, unit-tests, integration-tests, component-tests, e2e-tests, build-docker). Деплой не является частью этого workflow.

### AC-02: Пайплайн запускается при PR в main
- **Given** разработчик создал pull request в ветку `main`,
- **When** срабатывает триггер `pull_request`,
- **Then** запускаются этапы lint, unit-tests, integration-tests, component-tests, но НЕ e2e-tests и НЕ build-docker.

### AC-03: Lint и Type Check проходят успешно
- **Given** код соответствует правилам ESLint и TypeScript,
- **When** выполняется этап `lint`,
- **Then** `npm run lint` и `npm run type-check` завершаются с кодом 0.

### AC-04: Unit-тесты проходят успешно
- **Given** unit-тесты не требуют БД,
- **When** выполняется этап `unit-tests`,
- **Then** `npm run test:unit` завершается с кодом 0 после `npm run db:generate`.

### AC-05: Интеграционные тесты работают с PostgreSQL
- **Given** сервис PostgreSQL запущен через GitHub Actions services,
- **When** выполняется этап `integration-tests`,
- **Then** схема БД применена (`prisma db push`), тесты проходят с `DATABASE_URL=postgresql://test:test@localhost:5432/snt_test`.

### AC-06: E2E-тесты запускаются только на main
- **Given** пуш в ветку `main`,
- **When** запускается пайплайн,
- **Then** E2E-тесты выполняются после сборки (`npm run build`) и запуска приложения (`npm start`).
- **And** при PR в `main` E2E-тесты НЕ выполняются.

### AC-07: Docker-образ собран и запушен
- **Given** все тесты прошли успешно при пуше в `main`,
- **When** запускается этап `build-docker`,
- **Then** Docker-образ собран, тегами SHA и `latest`, и запушен в Docker Hub.

### AC-08: Пайплайн падает при ошибке линтинга
- **Given** в коде есть нарушение правил ESLint,
- **When** выполняется этап `lint`,
- **Then** пайплайн останавливается на этапе lint и зависимые этапы не запускаются.

### AC-09: Артефакты E2E-тестов сохранены
- **Given** E2E-тесты завершились (успешно или с ошибкой),
- **When** завершается этап `e2e-tests`,
- **Then** результаты тестов сохранены как артефакт `e2e-test-results` и доступны для скачивания.

### AC-10: Конкурирующие запуски отменяются
- **Given** два пуша в `main` сделаны быстро друг за другом,
- **When** второй пуш триггерит новый запуск пайплайна,
- **Then** первый запуск отменён, выполняется только последний.

## 7. Структура пайплайна (схема зависимостей)

```
push to main/develop, PR to main
        │
        ├────── lint ──────────────────────────────┐
        ├────── unit-tests ────────────────────────┤
        ├────── integration-tests ─────────────────┤
        └────── component-tests ───────────────────┤
                                                    │
                                                    ▼
                                         (all must pass)
                                                    │
            ┌───────────────────────────────────────┤
            ▼                                       │
    [push main only] e2e-tests                     │
            │                                       │
            ▼                                       │
    [push main only] build-docker ◄────────────────┤
```
