## Статус
[Согласовано]

## 0. Общие положения

Настоящий документ описывает порядок управления (создание, изменение, удаление) функциональными требованиями проекта.

### 0.1 Связанные документы

| Документ | Назначение |
|----------|------------|
| [`.roo/rules/fr-rules.md`](../../.roo/rules/fr-rules.md) | Организация хранения и структура спецификаций |
| [`.roo/rules/architecture.md`](../../.roo/rules/architecture.md) | Spec-driven development, архитектурные правила |
| [`.roo/rules/data-model-rules.md`](../../.roo/rules/data-model-rules.md) | Правила изменения модели данных |
| [`.roo/rules/change-rules.md`](../../.roo/rules/change-rules.md) | Общий порядок внесения изменений |

### 0.2 Принципы

1. **Спецификация — единственный источник истины.** Код пишется только на основе согласованных требований.
2. **Изменения начинаются с анализа.** Прежде чем вносить изменения, необходимо оценить их влияние.
3. **Требования разбиты по доменам.** Каждый домен — отдельная предметная область.
4. **Каждое изменение согласовывается.** Результат анализа обсуждается до реализации.

## 1. Организация требований по доменам

### 1.1 Нумерация

- Каждый домен имеет двузначный числовой код: `01`, `02`, ...
- Каждое требование нумеруется в формате: `FR-<код домена>-<номер требования>`
- Нумерация требований внутри домена — сквозная

**Примеры:**
- `FR-01-001` — первое требование домена «Управление пользователями»
- `FR-02-003` — третье требование домена «Управление сообществом»
- `FR-06-012` — двенадцатое требование домена «Бухгалтерия»

### 1.2 Реестр доменов

| Код | Домен | Файл | Описание |
|-----|-------|------|----------|
| 00 | Обзор | `00-overview.md` | Введение, глоссарий, общая структура |
| 01 | Управление пользователями | `01-user-management.md` | Аутентификация, пользователи, роли, доступ |
| 02 | Управление сообществом | `02-community-management.md` | Сообщества, участники, участки |
| 03 | Публикации | `03-publications.md` | Документы, объявления, страницы |
| 04 | Голосования | `04-voting.md` | Голосования, инициативы, результаты |
| 05 | Коммуникации | `05-communication.md` | Чаты, уведомления, форумы |
| 06 | Бухгалтерия | `06-accounting.md` | Платежи, начисления, взносы, баланс |
| 07 | Состояние UI | `07-ui-state-persistence.md` | Управление состоянием UI, URL-параметры |
| 08 | Технические спецификации | `08-technical-specs.md` | API, интеграции, инфраструктура |

### 1.3 Типы спецификаций

| Тип | Описание | Примеры |
|-----|----------|---------|
| **Бизнес-домены** | Описание бизнес-областей и сущностей | `01-user-management.md`, `02-community-management.md` |

## 2. Процесс управления требованиями

### 2.1 Анализ существующих требований

При получении запроса на изменение функциональности:

1. Просканировать существующие функциональные требования в `docs/specs/`
2. Определить затронутые требования и домены
3. Оценить тип необходимого изменения:
   - **Новое требование** → перейти к [2.2](#22-добавление-нового-требования)
   - **Изменение существующего** → перейти к [2.3](#23-изменение-существующего-требования)
   - **Удаление существующего** → перейти к [2.4](#24-удаление-существующего-требования)
4. Обсудить предлагаемые изменения с пользователем
5. По результатам обсуждения — реализовать изменения

### 2.2 Добавление нового требования

1. **Определить домен**
   - Найти подходящий домен в реестре (см. [1.2](#12-реестр-доменов))
   - Если ни один домен не подходит — подготовить описание нового домена
   - Обсудить выбор домена с пользователем

2. **Определить номер требования**
   - Найти максимальный номер требования в домене
   - Присвоить следующий номер: `FR-<код домена>-<следующий номер>`

3. **Описать требование**
   - Использовать шаблон из [раздела 3.2](#32-шаблон-требования)
   - Заполнить все обязательные поля
   - Указать связанные сущности из `specs/models/`

4. **Согласовать**
   - Установить статус «На обсуждении»
   - Обсудить с пользователем
   - При согласовании — установить статус «Согласовано»

5. **Проверить целостность**
   - Убедиться, что требование не дублирует существующие
   - Проверить связи с моделью данных
   - Проверить зависимости от других требований

### 2.3 Изменение существующего требования

1. **Проанализировать текущее состояние**
   - Найти требование по номеру `FR-XX-NNN`
   - Зафиксировать текущую редакцию требования
   - Определить причину изменения (новые вводные, уточнение, исправление ошибки)

2. **Оценить влияние изменения**
   - Выявить связанные требования (через раздел «Зависимости»)
   - Определить затронутые сущности модели данных (через `specs/models/`)
   - Найти потребителей требования в коде (UI, API, сервисы)
   - Оценить критичность:
     - **Некритическое**: уточнение формулировки, добавление критериев приёмки
     - **Критическое**: изменение поведения, нарушение обратной совместимости

3. **Подготовить изменения**
   - Для некритических изменений: обновить текст требования напрямую
   - Для критических изменений: подготовить план миграции (аналогично [data-model-rules.md](../../.roo/rules/data-model-rules.md) раздел 3.3)

4. **Обновить связанные артефакты** (если требуется)
   - Обновить DBML спецификацию в `specs/models/`

5. **Обсудить и согласовать**
   - Установить статус «На обсуждении»
   - Представить анализ влияния и предлагаемые изменения
   - При согласовании — установить статус «Согласовано»

6. **Зафиксировать изменение**
   - Добавить запись в «Историю изменений» требования
   - Указать причину, автора и дату изменения

### 2.4 Удаление существующего требования

1. **Проверить зависимости**
   - Найти требования, которые ссылаются на удаляемое (через раздел «Зависимости»)
   - Если есть зависимые требования — сначала разрешить зависимости:
     - Перенести зависимость на другое требование
     - Удалить зависимое требование одновременно
     - Отклонить удаление

2. **Найти потребителей требования**
   - Проверить использование в коде (UI, API, сервисы)
   - Проверить использование в модели данных (`prisma/schema.prisma`)
   - Проверить использование в тестах

3. **Оценить критичность удаления**
   - **Некритическое**: требование не реализовано или есть замена
   - **Критическое**: требование реализовано, нет прямой замены, удаление нарушает работу системы

4. **Подготовить план удаления**
   - Для некритического: удалить требование из документа
   - Для критического: провести депрекацию (см. шаг 5)

5. **Провести депрекацию** (для критических удалений)
   - Добавить пометку `@deprecated` в текст требования
   - Указать причину депрекации и альтернативу
   - Установить статус «Завершено»
   - Уведомить потребителей (обновить API документацию, код)
   - После истечения срока депрекации — удалить требование

6. **Зафиксировать удаление**
   - Удалить требование из файла домена
   - Перенумеровать оставшиеся требования (при необходимости)
   - Добавить запись в «Историю изменений» файла домена
   - Обновить связи в зависимых требованиях

## 3. Структура и шаблоны файлов требований

### 3.1 Структура домена

Каждый домен представляется отдельным файлом `docs/requirements/<код>-<название>.md`.

**Структура файла домена:**

```markdown
# <Название домена>

## Статус
[Черновик] / [На обсуждении] / [Согласовано] / [В реализации] / [Завершено]

---

## 1. Цель

Описание бизнес-цели домена.

## 2. Область применения

Где используется, какие роли вовлечены, границы функциональности.

## 3. Функциональные требования

### FR-XX-001: Название первого требования
**Описание:** Что система должна делать.
**Критерии приёмки:** Как проверить выполнение.

### FR-XX-002: Название второго требования
**Описание:** Что система должна делать.
**Критерии приёмки:** Как проверить выполнение.

## 4. Нефункциональные требования

### NFR-XX-001: Производительность
Метрики (время ответа, нагрузочные показатели).

### NFR-XX-002: Безопасность
Требования безопасности (аутентификация, авторизация, шифрование).

### NFR-XX-003: Доступность
Соответствие стандартам доступности (WCAG, ARIA).

## 5. Связанные сущности

| Сущность | Домен | Описание |
|----------|-------|----------|
| User | Core | Пользователь системы |

## 6. UI/UX требования

### 6.1 Экранные требования
Описание интерфейса, компоненты, лейаут.

### 6.2 Взаимодействие
Поведение при действиях пользователя, валидация, обратная связь.

## 7. Зависимости

- [ ] Блокирует: <FR-XX-NNN>
- [ ] Зависит от: <FR-XX-NNN>
- [ ] Связана с: <FR-XX-NNN>

## 8. История изменений

| Версия | Дата | Автор | Изменения |
|--------|------|-------|-----------|
| 1.0.0 | YYYY-MM-DD | Автор | Первоначальная версия |
```

### 3.2 Шаблон требования

При добавлении нового требования в файл домена используйте следующий шаблон:

```markdown
### FR-XX-NNN: Название требования

**Описание:** Что система должна делать. Чёткая, проверяемая формулировка.

**Критерии приёмки:**
1. Условие 1, которое можно проверить.
2. Условие 2, которое можно проверить.

**Приоритет:** Высокий / Средний / Низкий

**Связанные сущности:**
| Сущность | Домен | Операция |
|----------|-------|----------|
| Entity | Domain | CRUD |

**Зависимости:**
- Зависит от: FR-XX-NNN
- Блокирует: FR-XX-NNN
```

## 4. Процесс согласования

### 4.1 Статусы требований

| Статус | Описание | Допустимые переходы |
|--------|----------|---------------------|
| **Черновик** | Инициальное описание, можно редактировать без согласования | → На обсуждении |
| **На обсуждении** | Требует проверки и согласования | → Черновик, Согласовано |
| **Согласовано** | Утверждено, готово к разработке | → В реализации |
| **В реализации** | Разрабатывается, обновляется по мере прогресса | → Завершено, На обсуждении |
| **Завершено** | Реализовано и проверено | → На обсуждении (при обнаружении проблем) |

### 4.2 Критерии перехода между статусами

| Переход | Критерии |
|---------|----------|
| Черновик → На обсуждении | Требование полностью описано, заполнены все обязательные поля шаблона |
| На обсуждении → Согласовано | Требование обсуждено с пользователем, нет противоречий с другими требованиями и моделью данных |
| На обсуждении → Черновик | Выявлены противоречия или неполнота, требуется доработка |
| Согласовано → В реализации | Спецификация утверждена, разработчик назначен |
| В реализации → Завершено | Код написан, тесты пройдены, код-ревью завершено |
| В реализации → На обсуждении | Выявлены проблемы при реализации, требуется уточнение требования |
| Завершено → На обсуждении | Обнаружены проблемы в продакшене или изменение бизнес-требований |

### 4.3 Правила изменения статуса

1. Статус требования может быть изменён только после выполнения критериев перехода.
2. Каждое изменение статуса фиксируется в «Истории изменений» файла домена.
3. Требование в статусе «Согласовано» или «В реализации» нельзя удалять — только через процедуру депрекации (см. [2.4](#24-удаление-существующего-требования)).

## 5. Взаимосвязь с моделью данных

### 5.1 Принцип согласованности

Изменения функциональных требований могут требовать изменений в модели данных. Порядок согласования:

1. **Изменение требования → проверка модели данных.** При каждом изменении FR проверить, затронуты ли сущности в `specs/models/`.
2. **Изменение модели данных → проверка требований.** При изменении модели данных проверить, какие FR ссылаются на изменяемые сущности.

### 5.2 Процесс координации

```
Изменение FR → Анализ влияния на модель → Обновление DBML → Обновление Prisma → Миграция
                                     ↓
                              Обновление MD описания
                                     ↓
                              Обновление TypeScript типов
```

1. При добавлении/изменении FR, который затрагивает сущности данных — обновить DBML спецификацию в `specs/models/`
2. Обновить MD описание сущностей в `specs/models/`
3. Обновить `prisma/schema.prisma` (согласно `.roo/rules/data-model-rules.md`)
4. Создать и применить миграцию
5. Обновить TypeScript типы в `src/types/`

### 5.3 Чек-лист проверки

- [ ] Требование не противоречит концептуальной модели (`specs/models/*.dbml`)
- [ ] Связанные сущности указаны в разделе «Связанные сущности»
- [ ] Операции над сущностями (CRUD) описаны явно
- [ ] Изменения модели данных задокументированы в `specs/models/*.md`
