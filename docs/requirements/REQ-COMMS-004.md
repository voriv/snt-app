# REQ-COMMS-004: Запрет создания дублирующихся личных диалогов

## 1. Бизнес-контекст и Цель

**Проблема:** В текущей реализации система общения (REQ-COMMS-001) позволяет пользователю начать личный диалог с другим пользователем, но отсутствует чёткое бизнес-правило на уровне требований, запрещающее создание нескольких диалогов между одной и той же парой пользователей. Это может привести к появлению дублирующихся диалогов, что затрудняет навигацию и дезориентирует пользователей.

* **Бизнес-цель:** Обеспечить инвариант системы — между двумя пользователями может существовать не более одного активного личного диалога. Предотвратить создание дубликатов на уровне бизнес-логики (backend-валидация) и обеспечить корректный UX на клиенте (автоматическое перенаправление в существующий диалог).
* **Стейкхолдеры / Пользователи:**
  * Члены СНТ (MEMBER) — основные получатели выгоды: не видят дублирующиеся диалоги в списке
  * Администраторы (ADMIN) — используют те же функции личных сообщений
  * Product Owner — контроль качества UX

---

## 2. Бизнес-правила и Логика (Business Rules)

* **BR-01:** Между двумя пользователями может существовать не более одного личного диалога (type = DIRECT).
* **BR-02:** При попытке начать диалог с пользователем, с которым уже существует активный личный диалог, система не создаёт новый диалог, а перенаправляет инициатора в существующий.
* **BR-03:** Личный диалог считается активным, пока он не был удалён администратором. Пользователь не может удалить личный диалог.
* **BR-04:** Проверка существования диалога выполняется на стороне сервера (backend) для предотвращения обхода через прямой вызов API.
* **BR-05:** На стороне клиента (UI) при отображении списка пользователей для начала диалога те, с кем уже есть активный диалог, должны быть визуально отмечены (например, подпись «Диалог существует» или кнопка «Открыть диалог» вместо «Написать»).
* **BR-06:** Уникальность диалога на уровне БД обеспечивается уникальным ограничением (unique constraint) на комбинацию участников для типа DIRECT.

## 3. Функциональные требования

### Backend — валидация и логика

* **FR-REQ-COMMS-004-01:** При вызове API создания диалога (`POST /api/v1/conversations`) сервис должен проверить, существует ли уже личный диалог (type = DIRECT) между текущим пользователем (currentUserId) и целевым пользователем (participantId).
* **FR-REQ-COMMS-004-02:** Если диалог уже существует, API должен вернуть HTTP 409 (Conflict) с телом `{ conversationId: "existing-id", isNew: false }` и сообщением «Диалог с этим пользователем уже существует».
* **FR-REQ-COMMS-004-03:** Если диалог не существует, API должен создать новый диалог и вернуть HTTP 201 с телом `{ conversationId: "new-id", isNew: true }`.
* **FR-REQ-COMMS-004-04:** В `CommsService.startConversation()` должна быть реализована логика: проверка на себя → проверка на блокировку → **поиск существующего диалога** → создание нового (если не найден).
* **FR-REQ-COMMS-004-05:** В репозитории (`ICommsRepository`) должен быть метод `findConversationBetween(userAId, userBId)`, выполняющий поиск личного диалога между двумя указанными пользователями.

### Frontend — UX

* **FR-REQ-COMMS-004-06:** На странице выбора собеседника (`/dashboard/comms/messages/new`) для пользователей, с которыми уже есть активный диалог, должна отображаться кнопка «Открыть диалог» вместо «Написать сообщение».
* **FR-REQ-COMMS-004-07:** При клике на кнопку «Открыть диалог» пользователь немедленно перенаправляется на `/dashboard/comms/messages/:conversationId` существующего диалога.
* **FR-REQ-COMMS-004-08:** При получении ответа 409 от API (`POST /api/v1/conversations`), клиент должен извлечь `conversationId` из ответа и выполнить редирект на `/dashboard/comms/messages/:conversationId`.
* **FR-REQ-COMMS-004-09:** При загрузке страницы `/dashboard/comms/messages/new` клиент должен запросить список существующих диалогов текущего пользователя для корректного отображения кнопок («Написать» vs «Открыть»).

## 5. Нефункциональные требования (NFR) и Ограничения

* **NFR-01 (Производительность):** Проверка существования диалога (`findConversationBetween`) должна выполняться за < 50 мс (индексированный запрос).
* **NFR-02 (Безопасность):** Валидация на стороне сервера обязательна — клиентскую проверку нельзя полагать как единственную защиту.
* **NFR-03 (Консистентность):** Инвариант «один диалог на пару пользователей» должен сохраняться даже при параллельных запросах от одного пользователя (race condition предотвращается unique constraint в БД).
* **NFR-04 (Доступность):** Кнопки «Написать» и «Открыть диалог» должны иметь различающиеся aria-label для скринридеров.

## 6. Исключения и Граничные кейсы (Edge Cases)

* **EC-01:** Пользователь пытается создать диалог сам с собой — система должна вернуть ошибку 400 (Bad Request) с сообщением «Нельзя создать диалог с самим собой». (Уже покрывается US-21-02 AC-1.5.)
* **EC-02:** Пользователь пытается создать диалог с заблокированным пользователем — система должна вернуть ошибку 403 (Forbidden) с сообщением «Нельзя написать заблокированному пользователю». (Уже покрывается US-21-02 AC-1.6.)
* **EC-03:** Два параллельных запроса на создание диалога с одним и тем же пользователем (race condition) — первый запрос создаёт диалог, второй получает 409 из-за unique constraint в БД.
* **EC-04:** Пользователь открывает страницу `/dashboard/comms/messages/new` и сразу кликает на пользователя до загрузки списка диалогов — система выполняет API-запрос на создание, получает 409 и корректно редиректит в существующий диалог.
* **EC-05:** Диалог был удалён администратором после того, как пользователь увидел его в списке — при попытке открыть диалог API возвращает 404, и пользователь перенаправляется на страницу «Диалог не найден».

## 7. Критерии приёмки

### Backend

**AC-01: Создание нового диалога с пользователем, у которого нет активного диалога**
- **Given:** Пользователь A не имеет личного диалога с Пользователем B
- **When:** Пользователь A вызывает `POST /api/v1/conversations` с `{ participantId: "B" }`
- **Then:** Сервер создаёт новый диалог, возвращает 201 с `{ conversationId: "...", isNew: true }`

**AC-02: Попытка создать диалог с пользователем, у которого уже есть активный диалог**
- **Given:** Пользователь A уже имеет личный диалог (id="conv-123") с Пользователем B
- **When:** Пользователь A вызывает `POST /api/v1/conversations` с `{ participantId: "B" }`
- **Then:** Сервер возвращает 409 с `{ conversationId: "conv-123", isNew: false }` и сообщением «Диалог с этим пользователем уже существует»

**AC-03: Race condition — параллельные запросы**
- **Given:** Пользователь A не имеет диалога с Пользователем B
- **When:** Два параллельных запроса `POST /api/v1/conversations` с `{ participantId: "B" }`
- **Then:** Один запрос создаёт диалог (201), второй получает 409

**AC-04: Поиск диалога между пользователями в репозитории**
- **Given:** Существует диалог между пользователем A и B
- **When:** Вызывается `findConversationBetween(A, B)` или `findConversationBetween(B, A)`
- **Then:** Возвращается тот же диалог (независимо от порядка аргументов)

### Frontend

**AC-05: Отображение кнопки «Открыть диалог» для существующего диалога**
- **Given:** Пользователь A заходит на `/dashboard/comms/messages/new` и имеет диалог с Пользователем B
- **When:** Страница загружает список пользователей
- **Then:** Рядом с Пользователем B отображается кнопка «Открыть диалог» (не «Написать сообщение»)

**AC-06: Редирект в существующий диалог при клике**
- **Given:** Рядом с Пользователем B отображается кнопка «Открыть диалог»
- **When:** Пользователь A кликает на кнопку
- **Then:** Происходит редирект на `/dashboard/comms/messages/:conversationId` существующего диалога

**AC-07: Обработка 409 при прямом вызове API**
- **Given:** Пользователь кликает «Написать» до загрузки данных о существующих диалогах
- **When:** API возвращает 409 с `{ conversationId: "conv-123" }`
- **Then:** Клиент извлекает conversationId и редиректит на `/dashboard/comms/messages/conv-123`
