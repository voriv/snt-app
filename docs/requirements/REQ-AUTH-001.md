# REQ-AUTH-001: Аутентификация и регистрация

## 1. Бизнес-контекст и Цель

*Система управления СНТ Берёзки-НТ требует механизма аутентификации для защиты персональных данных садоводов и разграничения прав доступа к функционалу приложения.*

* **Бизнес-цель:** Обеспечить безопасный доступ авторизованных пользователей к информации об участках и участниках СНТ, предотвращая несанкционированный доступ к данным.
* **Стейкхолдеры / Пользователи:** Все пользователи системы (гости, члены СНТ, администраторы), администраторы приложения.

## 2. Бизнес-правила и Логика (Business Rules)

* **BR-01:** Каждый пользователь должен иметь уникальный email для регистрации
* **BR-02:** Пароли хранятся только в зашифрованном виде и никогда не возвращаются в ответе системе
* **BR-03:** При аутентификации используется одинаковое сообщение ошибки для "email не найден" и "пароль неверный" — защита от атак перебором
* **BR-04:** Новым пользователям автоматически назначается базовая роль до подтверждения
* **BR-05:** Разделы дашборда защищены — требуется авторизация
* **BR-06:** Авторизованные пользователи перенаправляются с главной страницы на дашборд
* **BR-07:** Публичные страницы (главная, вход, регистрация) доступны без авторизации
* **BR-08:** Для смены пароля требуется подтверждение текущего пароля (защита от несанкционированной смены)
* **BR-09:** Новый пароль не может совпадать с текущим
* **BR-10:** Новый пароль: минимум 6 символов
* **BR-11:** При успешной смене пароля все активные сессии пользователя сохраняются (не инвалидируются) — так как смена инициирована самим пользователем
* **BR-12:** Пароли хранятся только в зашифрованном виде (bcrypt)

## 3. Функциональные требования

* **FR-01:** Система должна поддерживать регистрацию нового пользователя по email и паролю с валидацией данных
* **FR-02:** Система должна поддерживать вход (аутентификацию) по email и паролю
* **FR-03:** Система должна поддерживать выход (удаление сессии)
* **FR-04:** Система должна защищать маршруты дашборда — редирект неавторизованных пользователей на страницу входа
* **FR-05:** Система должна поддерживать управление сессиями для клиентских компонентов
* **FR-06:** Система должна отображать стартовую страницу (главная) с описанием приложения и кнопкой "Войти"
* **FR-07:** Система должна отображать страницу входа с формой email/пароль
* **FR-08:** Система должна отображать страницу регистрации с формой email/пароль/подтверждение пароля
* **FR-09:** Система должна поддерживать смену пароля авторизованным пользователем через API: `PUT /api/v1/auth/password` с телом `{ currentPassword, newPassword, confirmPasswordNew }`
* **FR-10:** Система должна проверять корректность текущего пароля перед применением нового
* **FR-11:** Система должна валидировать новый пароль: мин. длина 6 символов, совпадение с подтверждением
* **FR-12:** Система должна предоставлять UI-страницу `/settings/security` с формой смены пароля

## 5. Нефункциональные требования (NFR) и Ограничения

* **Безопасность:**
  * Пароли хешируются с использованием стойкого алгоритма
  * Email приводится к нижнему регистру и обрезается
  * Одинаковое сообщение ошибки для всех сценариев неудачной аутентификации
  * Сессии управляются через встроенный механизм веб-фреймворка
  * CSRF защита
* **Производительность:**
  * Регистрация: < 500ms (включая хеширование пароля)
  * Аутентификация: < 300ms
  * Проверка сессии: < 50ms
  * Смена пароля: < 500ms (включая хеширование bcrypt)
* **Доступность:** Работа в режиме 24/7, время простоя не более 1 часа в год
* **Удобство (UX):**
  * Сообщения об ошибках на русском языке, валидация в реальном времени на клиенте
  * Ошибка неверного текущего пароля: общее сообщение "Неверный текущий пароль" (не раскрывать, что пароль неверный vs сессия истекла)

## 6. Исключения и Граничные кейсы (Edge Cases)

* **EC-01:** Если email уже зарегистрирован — система возвращает понятное сообщение о дублировании
* **EC-02:** Если пользователь вводит неверный пароль — система возвращает общее сообщение "Неверный email или пароль"
* **EC-03:** Если сессия истекла во время использования — редирект на страницу входа с сохранением адреса, куда хотел попасть пользователь
* **EC-04:** Если пользователь пытается получить доступ к разделу дашборда без авторизации — редирект на страницу входа
* **EC-05:** Если механизм защиты маршрутов недоступен — страница отображается без редиректа
* **EC-06:** Если текущий пароль неверный — ошибка "Неверный текущий пароль"
* **EC-07:** Если новый пароль совпадает с текущим — ошибка "Новый пароль не может совпадать с текущим"
* **EC-08:** Если новый пароль менее 6 символов — ошибка валидации
* **EC-09:** Если новый пароль и подтверждение не совпадают — ошибка "Пароли не совпадают"

## 7. Критерии приёмки

1. Пользователь может зарегистрироваться с уникальным email и паролем — возвращается данные пользователя без пароля
2. Пользователь может войти с правильными учётными данными — создаётся сессия
3. Неправильные учётные данные возвращают общее сообщение "Неверный email или пароль"
4. Неавторизованный пользователь перенаправляется с разделов дашборда на страницу входа
5. Авторизованный пользователь перенаправляется с главной страницы на дашборд
6. Страница входа отображает форму входа без ошибок
7. Страница регистрации отображает форму регистрации с валидацией
8. Кнопка "Выйти" удаляет сессию и перенаправляет на страницу входа
9. Пользователь может сменить пароль, введя корректный текущий + новый (≥6 символов) + подтверждение
10. При неверном текущем пароле — отклонение с сообщением
11. При совпадении нового и текущего пароля — отклонение с сообщением
12. При коротком пароле (<6) — ошибка валидации
13. После смены пароля пользователь может войти с новым паролем
