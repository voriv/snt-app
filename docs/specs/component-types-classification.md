# Классификация типов компонентов: необходимость спецификаций

## 1. Компоненты, ТРЕБУЮЩИЕ спецификацию

### 1.1 UI Component (Client Component)

**Расположение:** `src/components/`

**Примеры:** `<Button />`, `<DataTable />`, `<UserForm />`

**Почему нужна спецификация:**
- Публичный API (props, события, слоты) — это контракт между компонентом и потребителями
- Обеспечивает переиспользование компонента разными разработчиками
- Позволяет заменять реализацию без изменения потребителей
- Критично для Design System и командной работы

**Требования к спецификации:**
- Интерфейс props с описанием каждого свойства
- Описание событий (callbacks)
- Примеры использования
- Описание поведения (side effects при рендере)
- Зависимости от других UI компонентов

---

### 1.2 UI Component (Server Component)

**Расположение:** `src/components/`, `src/app/`

**Примеры:** `<UserProfile />`, `<PageContent />`

**Почему нужна спецификация:**
- Публичный API (props, данные) — контракт для потребителей
- Зависимости от данных (queries, mutations)
- Влияние на UX (hydration, suspense boundaries)
- Безопасность (какие данные доступны на сервере)

**Требования к спецификации:**
- Интерфейс props с описанием каждого свойства
- Описание данных, которые получает компонент
- Описание вывода (что рендерит)
- Зависимости от серверных ресурсов (БД, API)
- Поведение при ошибках (error boundary)

---

### 1.3 API Router

**Расположение:** `src/app/api/`, `src/routes/`

**Примеры:** `POST /api/users`, `GET /api/charges`

**Почему нужна спецификация:**
- Это публичный интерфейс интеграции
- Определяет контракты для клиентов (web, mobile, third-party)
- Критичен для обратной совместимости
- Определяет безопасность (auth, authorization)

**Требования к спецификации:**
- HTTP метод и путь
- Требования аутентификации/авторизации
- Входные данные (query params, body, headers)
- Выходные данные (response body, status codes)
- Ошибки и коды ответов
- Лимиты и rate limiting

---

### 1.4 Service

**Расположение:** `src/services/`, `src/lib/services/`

**Примеры:** `UserService`, `PaymentService`, `NotificationService`

**Почему нужна спецификация:**
- Бизнес-логика изолирована в сервисы
- Публичный API сервиса — основной контракт для layer architecture
- Сложные операции требуют документирования бизнес-правил
- Обеспечивает тестируемость (mock-интерфейсы)

**Требования к спецификации:**
- Публичные методы с описаниями
- Входные и выходные данные каждого метода
- Бизнес-правила и валидация
- краткое опиаание алгоритма
- Побочные эффекты (отправка email, запись в БД)
- Исключения и ошибки
- Зависимости от других сервисов/repositories

---

### 1.5 Repository

**Расположение:** `src/repositories/`, `src/lib/repositories/`

**Примеры:** `UserRepository`, `ChargeRepository`

**Почему нужна спецификация:**
- Определяет контракт доступа к данным
- Обеспечивает независимость от ORM/хранилища
- Критичен для тестирования (mock repositories)
- Определяет операции CRUD и query patterns

**Требования к спецификации:**
- Публичные методы (find, create, update, delete)
- Входные параметры и возвращаемые типы
- Логика запросов (фильтрация, пагинация, сортировка)
- Транзакционное поведение
- Зависимости от базы данных

---

## 2. Компоненты, НЕ ТРЕБУЮЩИе отдельной спецификации

### 2.1 DTO (Data Transfer Object)

**Расположение:** `src/dto/`, `src/types/`

**Примеры:** `CreateUserDto`, `UserResponseDto`

**Почему НЕ нужна отдельная спецификация:**
- DTO — это просто типы данных (interfaces, types)
- Их структура описывается в спецификациях потребителей:
  - API Router спецификация описывает вход/выход DTO
  - Service спецификация описывает использование DTO
- DTO не имеют поведения, только данные
- Изменение DTO автоматически отражается в спецификациях потребителей

**Альтернатива:**
- DTO определяются через TypeScript interfaces/types
- Описываются в разделе "Входные/Выходные данные" спецификаций потребителей
- Могут использоваться как reference в других спецификациях

---

### 2.2 Schema (Zod/Yup Validation Schema)

**Расположение:** `src/schemas/`, `src/validations/`

**Примеры:** `CreateUserSchema`, `LoginSchema`

**Почему НЕ нужна отдельная спецификация:**
- Schema — это реализация валидации для DTO
- Являются технической деталью реализации
- Бизнес-правила описываются в спецификациях Service/API
- Schema могут меняться без изменения бизнес-контракта

**Альтернатива:**
- Schema определяются в коде (TypeScript)
- Правила валидации описываются в спецификациях потребителей
- Schema используются для автоматической генерации документации (OpenAPI)

---

### 2.3 UI Helper Functions

**Расположение:** `src/components/ui/`, `src/lib/`

**Примеры:** `cn()`, `formatDate()`, `capitalize()`

**Почему НЕ нужна отдельная спецификация:**
- Простые утилитарные функции с очевидным поведением
- Обычно имеют тривиальные контракты (вход → выход)
- Документируются JSDoc прямо в коде
- Не имеют побочных эффектов или сложных зависимостей

**Альтернатива:**
- JSDoc комментарии в коде
- TypeScript типы обеспечивают type safety

---

### 2.4 Hooks (Internal Utilities)

**Расположение:** `src/hooks/`, `src/lib/hooks/`

**Примеры:** `useDebounce`, `useMediaQuery`

**Почему НЕ нужна отдельная спецификация (для внутренних):**
- Внутренние хуки — это утилиты для UI компонентов
- Их API — это props и возвращаемые значения (описывается в коде)
- Используются только внутри компонента или как вспомогательные

**Исключение:**
- Если хук является частью Design System и используется многими компонентами — нужна спецификация как у UI Component

---

### 2.5 Configuration Files

**Расположение:** `next.config.ts`, `tailwind.config.ts`, `tsconfig.json`

**Почему НЕ нужна отдельная спецификация:**
- Конфигурационные файлы самодокументируемы
- Описываются в `README.md` проекта
- Изменения тривиальны и очевидны

---

### 2.6 Test Files

**Расположение:** `src/**/*.test.ts`, `src/**/*.spec.ts`

**Почему НЕ нужна отдельная спецификация:**
- Тесты — это реализация верификации
- Описание проверок содержится в спецификациях компонентов
- Тесты меняются вместе с кодом

| **UI Component (Server)** | ✅ Требуется | Публичный API, зависимости от данных, поведение при ошибках |

## 4. Рекомендации

1. **Публичный API — критерий необходимости спецификации.** Если компонент имеет публичный API, используемый другими модулями, — нужна спецификация.

2. **Спецификация — не дублирование кода.** Спецификация описывает контракт, а не реализацию. Детали реализации (алгоритмы, имплементация методов) в спецификации не дублируются.

3. **Спецификации потребителей как alternativa.** DTO и Schema описываются в спецификациях тех компонентов, которые их используют (API Router, Service).

4. **Импортируемые определения.** Спецификации могут ссылаться на типы DTO/Schema через TypeScript import, не дублируя определения.

5. **Регулярный пересмотр.** Раз в спринт проверять, не стал ли компонент (без спецификации) публичным или сложным enough для необходимости спецификации.
