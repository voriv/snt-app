# Требования к спецификациям компонентов

## 1. Общие требования

### 1.1 Расположение
- Спецификации компонентов хранятся в `docs/specs/components/`
- Каждая спецификация — отдельный Markdown файл
- Именование файлов: `<тип>-<название>.md`

### 1.2 Структура директории
```
docs/specs/components/
├── README.md                    # Навигация и описание
├── ui/
│   ├── client/
│   │   ├── ui-button.md
│   │   └── ui-table.md
│   └── server/
│       ├── ui-user-profile.md
│       └── ui-page-content.md
├── api/
│   ├── api-create-user.md
│   └── api-get-charges.md
├── services/
│   ├── service-user.md
│   └── service-payment.md
└── repositories/
    ├── repository-user.md
    └── repository-charge.md
```

### 1.3 Метаданные спецификации (в начале каждого файла)

```markdown
---
тип: ui/client | ui/server | api | service | repository
название: ComponentName
статус: черновик | на обсуждении | согласовано | в реализации | завершено
автор: <имя>
дата-создания: YYYY-MM-DD
дата-обновления: YYYY-MM-DD
версия: X.Y.Z
---
```

### 1.4 Статусы спецификаций

| Статус | Описание |
|--------|----------|
| **Черновик** | Инициальное описание |
| **На обсуждении** | Требует согласования |
| **Согласовано** | Утверждена, готова к разработке |
| **В реализации** | Разрабатывается |
| **Завершено** | Реализована и проверена |

## 4. Спецификация API Router

### 4.1 Структура

```markdown
# API Endpoint: <Метод> <Path>

## Метаданные
(см. раздел 1.3)

## 1. Описание
Краткое описание назначения endpoint.

## 2. Endpoint

### URL
`<METHOD> /api/<version>/<resource>`

### Аутентификация
| Требование | Описание |
|------------|----------|
| Auth | 🔒 Требуется токен |
| Role | 👑 Роль: ADMIN / MEMBER / GUEST |

### Headers

| Заголовок | Тип | Обязательный | Описание |
|-----------|-----|--------------|----------|
| `Authorization` | `string` | Да | Bearer token |

### Query Parameters

| Параметр | Тип | Обязательный | По умолчанию | Описание |
|----------|-----|--------------|--------------|----------|
| `limit` | `number` | Нет | 20 | Лимит записей |

### Request Body

| Поле | Тип | Обязательный | Описание |
|------|-----|--------------|----------|
| `email` | `string` | Да | Email пользователя |

### Response

#### Успешный ответ (200/201)
```json
{
  "id": "string",
  "email": "string"
}
```

#### Ошибки

| Код | Тело | Описание |
|-----|------|----------|
| 400 | `{ "error": "string" }` | Неверный запрос |
| 401 | `{ "error": "Unauthorized" }` | Нет авторизации |
| 403 | `{ "error": "Forbidden" }` | Нет доступа |
| 404 | `{ "error": "Not found" }` | Ресурс не найден |
| 500 | `{ "error": "Internal error" }` | Серверная ошибка |

- Валидация данных

|-----------|-----|----------|

### Внешние
| Сервис | Описание |
|--------|----------|
| `email.send()` | Отправка email подтверждения |

## 5. Лимиты (Rate Limiting)
- Максимум запросов в минуту

## 5. Спецификация Service

> ℹ️ Подробный шаблон спецификации сервиса доступен в [`spec-service-template.md`](./components/services/spec-service-template.md)

### 5.1 Обязательные секции

Каждая спецификация сервиса **должна** содержать следующие разделы в указанном порядке:

1. **Описание** — назначение сервиса, границы ответственности (что входит / не входит), связанные домены и сущности
2. **Бизнес-правила** — валидация (VR-XXX) и бизнес-логика (BL-XXX) с уникальными идентификаторами
3. **API сервиса** — публичные методы с описанием входных/выходных параметров, побочных эффектов
4. **Входные данные** — типы DTO и Zod-схемы валидации
5. **Зависимости** — репозитории, сервисы, внешние пакеты
6. **Выходные данные** — типы возвращаемых значений (DTO, пагинация, и т.д.)
7. **Обработка ошибок** — классы ошибок, коды, HTTP-статусы, стратегии обработки
8. **Транзакции** — операции, требующие транзакционной целостности
9. **Тестирование** — сценарии unit и integration тестов
10. **Структура файлов** — расположение файлов в проекте

> ℹ️ Полная структура шаблона доступна в [`spec-service-template.md`](./components/services/spec-service-template.md)

### 5.2 Правила именования

| Элемент | Шаблон | Пример |
|---------|--------|--------|
| **Методы** | глагол + объект | `create`, `update`, `delete`, `getByEmail`, `findByProjectId` |
| **Входные типы** | `<Entity>Input`, `<Entity>CreateInput`, `<Entity>UpdateInput` | `PaymentCreateInput`, `UserUpdateInput` |
| **Типы запроса** | `<Entity>ListQuery` | `ChargeListQuery` |
| **Типы возвращаемых значений** | `<Entity>Detail`, `<Entity>Dto` | `PaymentDetail`, `UserDto` |
| **Пагинация** | `Paginated<Entity>Result` | `PaginatedPaymentResult` |
| **Классы ошибок** | `<Domain>Error`, `<Operation>Error` | `ValidationError`, `NotFoundError`, `PaymentConflictError` |
| **Файлы** | `src/services/<domain>-service.ts`, `src/services/<domain>-service.test.ts` | `src/services/payment-service.ts` |

### 5.3 Правила бизнес-логики

- Каждая бизнес-операция должна иметь уникальный ID правила формата `VR-XXX` (валидация) или `BL-XXX` (логика)
- Границы ответственности сервиса должны быть чётко определены: что входит и что **НЕ входит** в зону ответственности
- Запрещён прямой доступ к БД из сервиса — только через Repository-абстракцию
- Транзакции используются только когда необходима атомарность нескольких операций (создание + начисление, обновление + логирование)
- Каждая сервисная функция не должна превышать **50 строк** кода; при превышении — декомпозировать

### 5.4 Правила обработки ошибок

- Запрещено бросать generic `Error` или использовать `any` при обработке ошибок
- Каждая ошибка должна иметь:
  - Уникальный код ошибки (`ERR_<DOMAIN>_<CODE>`)
  - HTTP-статус (400, 401, 403, 404, 409, 500)
  - Описание условия выброса
- Обязательная типизация ошибок через error-классы (расширяющие `AppError` или `BaseServiceError`)
- Стратегия обработки должна быть описана для каждого публичного метода

### 5.5 Правила тестирования

| Тип теста | Обязательность | Охват |
|-----------|----------------|-------|
| **Unit-тесты** | Обязательно для всех публичных методов | ≥ 80% покрытия бизнес-логики |
| **Integration-тесты** | Обязательно для операций с побочными эффектами | Критические пользовательские сценарии |

- Каждый тест должен описывать: сценарий, входные данные, ожидаемый результат
- Тесты должны покрывать: успешные сценарии, edge cases (пустые данные, граничные значения), ошибки (валидация, конфликты, не найдено)
- Изолированность: тесты не должны зависеть друг от друга

### 5.6 Правила кода для ИИ при генерации

| Правило | Детали |
|---------|--------|
| **JSDoc** | Все публичные методы должны иметь JSDoc-аннотации с описанием параметров, возвращаемого значения и исключений |
| **Dependency Injection** | Зависимости внедряются через конструктор, а не создаются внутри методов |
| **Размер функций** | Максимум 50 строк; при превышении — разбить на приватные вспомогательные методы |
| **Типизация** | Запрещено использовать `any`, `unknown` (как обходной путь), `ts-ignore` |
| **Валидация** | Входные данные валидируются через Zod-схемы на границе сервиса |
| **Factory pattern** | Сервис должен иметь factory-функцию для создания экземпляра с зависимостями |
| **Чистота** | Никаких побочных эффектов вне явно описанных (отправка email, запись в лог, вызов внешнего API) |

### 5.7 Связь с другими спецификациями

При написании спецификации сервиса обязательно ссылаться на:

- **Repository** — [`<RepositoryName>()`](../repositories/<repository-name>.md) — для доступа к данным
- **Model** — [`<Entity>`](../../model/<domain>.md#<entity>) — для понимания структуры данных
- **API Router** — [`<EndpointName>()`](../api-routers/<api-router-name>.md) — если сервис используется через API
- **Другие сервисы** — [`<ServiceName>()`](./<service-name>.md) — если требуется межсервисное взаимодействие

## 6. Спецификация Repository

### 6.1 Структура

```markdown
# Repository: <Название репозитория>

## Метаданные
(см. раздел 1.3)

## 1. Описание
Назначение репозитория и данные, которыми управляет.

## 2. Публичный API

### Методы

| Метод | Сигнатура | Возвращает |
|-------|-----------|------------|
| findMany | `findMany(filters, options): Promise<T[]>` | Массив записей |
| findById | `findById(id: string): Promise<T \| null>` | Запись или null |
| create | `create(data: CreateDto): Promise<T>` | Созданная запись |
| update | `update(id: string, data: UpdateDto): Promise<T>` | Обновлённая запись |
| delete | `delete(id: string): Promise<boolean>` | Успех операции |

**Параметры запроса findMany:** limit (50), offset (0), orderBy ('createdAt'), orderDir ('desc')

### Транзакции
- Поддержка транзакций через Prisma `$transaction`

### Индексы
| Поле | Тип | Описание |
|------|-----|----------|
| `email` | Unique | Быстрый поиск по email |

## 3. Зависимости

| Компонент | Тип | Для чего |
|-----------|-----|----------|
| `prisma` | ORM | Доступ к БД |
| `@prisma/client` | Внешний | ORM клиент |

## 4. Пример

```typescript
const users = await repo.findMany({ isActive: true }, { limit: 10, orderBy: 'name' });
```

## 7. Общие требования к оформлению

### 7.1 Язык
- Основной язык — Русский (описания, комментарии)
- Техническая терминология — на Английском (имена функций, типы)

### 7.2 Форматирование
- Markdown с использованием стандартных элементов
- Code blocks с указанием языка
- Таблицы для структурирования данных
- Mermaid диаграммы для сложных потоков

### 7.3 Ссылки
- На другие спецификации: `[<Название спецификации>](./<путь>.md)`
- На код: [`functionName()`](../../../src/path/to/file.ts:line)
- На FR требования: `[FR-01-001](../../../docs/requirements/01-user-management.md#fr-01-001)`

### 7.4 Версионирование
- Версия спецификации: `MAJOR.MINOR.PATCH`
- `MAJOR` —breaking changes в API
- `MINOR` — новые возможности
- `PATCH` — исправления описания
