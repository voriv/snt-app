# 🎨 Интеграция UI Designer в Orchestrator Pipeline

## 1. Общее описание

UI Designer — это специализированный режим, который создаёт макеты UI на основе User Story и плана реализации. UI Designer работает **ПЕРЕД Component Spec** в пайплайне, обеспечивая Component Spec источником UI-требований.

### Позиция в пайплайне

```
Planner → Plan Validator → UI Designer → Component Spec → Code Layers
```

## 2. Когда вызывается

**Правило: UI Designer вызывается ВСЕГДА**, когда задача затрагивает UI (страницы, компоненты, формы, таблицы).

### Критерии вызова

| Критерий | Пример |
|----------|--------|
| US содержит AC с визуальным представлением | "Таблица отображает все участки" |
| US описывает формы | "Форма создания участка" |
| US описывает списки/детали | "Карточка пользователя" |
| US описывает dashboard | "Страница дашборда" |

### Когда НЕ вызывать

| Критерий | Пример |
|----------|--------|
| Backend-only (API без UI) | "Добавить API для отправки email" |
| Баги без UI-изменений | "Исправить SQL запрос" |
| Чистая документация | "Обновить README" |

## 3. Входные артефакты

UI Designer читает следующие артефакты:

### Обязательные
- `docs/plans/US-NN-realization-plan.md` — план реализации
- `docs/user-stories/US-NN.md` — User Story с AC

### Дизайн-система
- `docs/design/tokens/*.md` — токены (цвета, шрифты, отступы, радиусы, тени)
- `docs/design/components/*.md` — документация UI-компонентов (Button, Input, Card, Badge и т.д.)
- `docs/design/patterns/*.md` — шаблоны страниц (list, detail, form)

### Шаблоны
- `docs/templates/layout-template.md` — шаблон ASCII/Text макета
- `docs/templates/prototype-template.html` — шаблон HTML/CSS прототипа

## 4. Выходные артефакты

| Артефакт | Описание | Формат |
|----------|----------|--------|
| `docs/design/layouts/{feature}/layout.md` | ASCII/Text макет | Markdown |
| `docs/prototypes/{feature}/index.html` | HTML/CSS прототип | HTML (опционально) |

### Когда создавать HTML/CSS прототип

- >5 состояний компонента
- Сложные интерактивные элементы
- Drag-and-drop, таблицы с сортировкой
- Модальные окна, диалоги
- Анимации, переходы

### Когда достаточно ASCII/Text

- Форма с ≤5 полями
- Таблица с ≤5 колонками
- Список карточек
- Страница деталей (без сложного layout)

## 5. Процесс работы

### Шаг 0 — Чтение дизайн-системы
1. Прочитать `docs/design/components/*.md` — все UI-компоненты
2. Прочитать `docs/design/tokens/*.md` — все токены
3. Прочитать `docs/design/patterns/*.md` — шаблоны страниц
4. **НЕ читать код** из `src/components/features/` — feature-компоненты это код, а не дизайн-система

### Шаг 1 — Анализ US и плана
1. Прочитать User Story
2. Прочитать план реализации
3. Определить, какие AC требуют UI
4. Определить сложность экрана

### Шаг 2 — Создание макета
1. Выбрать формат (ASCII или HTML/CSS)
2. Создать макет по шаблону
3. Использовать UI-компоненты из дизайн-системы
4. Использовать абстрактные блоки для feature-компонентов (`[PlotList]`, `[UserProfile]`)

### Шаг 3 — Завершение
1. Записать `docs/design/layouts/{feature}/layout.md`
2. Если HTML/CSS — записать прототип
3. Вызвать `attempt_completion`
4. **Пользователь утверждает макет**

## 6. Абстрактные блоки

UI Designer использует абстрактные блоки для feature-компонентов, которые не входят в дизайн-систему:

| Блок | Описание |
|------|----------|
| `[PlotList]` | Список участков (таблица или карточки) |
| `[PlotForm]` | Форма создания/редактирования участка |
| `[UserProfile]` | Карточка профиля пользователя |
| `[UserAvatar]` | Аватар пользователя |
| `[ThemeSwitcher]` | Переключатель темы |

### Правила абстрактных блоков

1. **Именование:** PascalCase, square brackets `[ComponentName]`
2. **Описание:** В макете опиши, что блок делает
3. **Props:** Укажи основные props в комментариях
4. **Не пиши код:** Абстрактные блоки — это плейсхолдеры

### Пример

```markdown
## Зона: Основной контент
```
+---------------------------------------------------+
| [PlotList]                                        |
|                                                   |
| Props:                                            |
|   - plots: Plot[]                                 |
|   - onEdit: (id: string) => void                  |
|   - onDelete: (id: string) => void                |
|                                                   |
| Содержит:                                         |
|   - Таблица с колонками                           |
|   - Кнопки "Редактировать" / "Удалить"            |
|   - Пустое состояние                              |
+---------------------------------------------------+
```

## 7. Передача в Component Spec

### Что читает Component Spec

Component Spec читает `docs/design/layouts/{feature}/layout.md` и извлекает:

1. **UI компоненты** — конкретные компоненты из дизайн-системы (Button, Input, Card)
2. **Абстрактные блоки** — feature-компоненты (`[PlotList]`, `[PlotForm]`)
3. **Композицию страницы** — как компоненты располагаются
4. **Хуки** — если указаны в макете

### Фаза 1.5 в Component Spec

Component Spec выполняет дополнительную фазу **"Анализ макета UI"**:

```
Фаза 1 — Анализ (план, US, модель данных)
    ↓
Фаза 1.5 — Анализ макета UI (layout.md)
    ↓
Фаза 2 — Декомпозиция (план + макет)
    ↓
Фаза 3 — Спецификация по слоям
    ↓
Фаза 4 — Создание скелетов
    ↓
Фаза 5 — Завершение
```

### Что происходит в Фазе 1.5

1. Прочитать `docs/design/layouts/{feature}/layout.md`
2. Извлечь UI-компоненты
3. Извлечь абстрактные блоки
4. Определить композицию страницы
5. Сопоставить с планом реализации

### Влияние на спецификацию

| Источник | Что определяет |
|----------|----------------|
| План | Функциональные блоки, зависимости, задачи |
| Макет (layout.md) | UI компоненты, композиция, props, состояния |
| Дизайн-система | Реализация UI-компонентов (Button, Input и т.д.) |

## 8. Обновление макетов

### Правило перезаписи

**Каждый вызов UI Designer ПЕРЕЗАПИСЫВАЕТ layout.md.**

Обоснование:
- План может измениться
- US могут измениться
- Дизайн-система может обновиться
- Каждый макет создаётся на основе актуальных данных

### Процесс обновления

1. UI Designer читает актуальные артефакты
2. Создаёт новый макет
3. Перезаписывает `docs/design/layouts/{feature}/layout.md`
4. Component Spec читает обновлённый макет

## 9. Подтверждение пользователя

### Когда требуется

**Всегда.** После создания макета:

1. UI Designer вызывает `attempt_completion` с макетом
2. Пользователь видит макет
3. Пользователь утверждает (или просит изменения)
4. После утверждения — Orchestrator передаёт управление Component Spec

### Формат подтверждения

```markdown
## Макет UI для US-NN

### Экраны
1. Список участков (ASCII)
2. Форма создания (ASCII)

### Файлы
- `docs/design/layouts/plots/layout.md` ✅ Создан

### Использованные компоненты
- Button, Input, Card, Badge, Table
- [PlotList] (абстрактный)
- [PlotForm] (абстрактный)

---

Утвердить макет? (да/нет/правки)
```

## 11. Пример работы

### Вход
- US-12: Отображение списка участков
- План реализации US-12

### Процесс UI Designer
1. Читает US-12 + план
2. Читает дизайн-систему (tokens, components, patterns)
3. Создаёт ASCII макет:
   - Header с заголовком
   - Зона списка участков
   - Зона пустого состояния
   - Зона загрузки
   - Зона ошибок

### Выход
- `docs/design/layouts/plots/layout.md` — ASCII макет

### Передача в Component Spec
Component Spec читает layout.md и:
1. Видит `[PlotList]` абстрактный блок
2. Создаёт скелет `PlotList.tsx`
3. Видит Button/Input/Card — использует дизайн-систему
4. Видит композицию — создаёт page.tsx с компоновкой

## 12. Часто задаваемые вопросы

### Q: Зачем UI Designer ПЕРЕД Component Spec?
**A:** Дизайн влияет на UI-компоненты и страницы. Component Spec нужно знать, что создавать и как компоновать.

### Q: UI Designer знает про существующие feature-компоненты?
**A:** Нет. UI Designer использует абстрактные блоки `[PlotList]` для feature-компонентов. Это обеспечивает чистое разделение: дизайн ≠ код.

### Q: Что если UI Designer создаст макет с компонентами, которых нет в дизайн-системе?
**A:** UI Designer должен использовать только компоненты из `docs/design/components/`. Если нужен новый компонент — он создаёт абстрактный блок.

### Q: Кто отвечает за дизайн-систему?
**A:** UI Designer читает дизайн-систему. Расширение дизайн-системы — отдельная задача.

### Q: Может ли Component Spec игнорировать макет?
**A:** Нет. Component Spec ОБЯЗАН использовать layout.md как источник UI-требований.

### Q: Что если план не затрагивает UI?
**A:** UI Designer не вызывается. Component Spec создаёт спецификацию только на основе плана.
