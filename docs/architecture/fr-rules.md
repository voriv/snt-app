## Стандарт именования файлов

- **Формат:** `FR-<двузначный-номер>-<название-через-дефис>.md`
- **Пример:** `FR-01-user-management.md`
- **Порядок:** Двухзначные префиксы для естественной сортировки

## Правила разработки спецификаций

### 1. Приоритет спецификаций над кодом

Согласно `.roo/rules/architecture.md`:
- **Никогда не писать код вслепую**
- Перед созданием или изменением файла **НАЙТИ** соответствующий файл спецификации в `specs/`
- Если спецификация не существует, **запросить переключение в Architect Mode** для создания спецификации
- Спецификация является **единственным источником истины**

### 2. Согласованность с моделью данных

Согласно `.roo/rules/data-model-rules.md`:
- Файлы спецификаций должны соответствовать доменам из `specs/models/`
- Изменения начинаются с концептуальной модели
- ORM модель (Prisma) следует за концептуальной моделью

### 3. Типы спецификаций

| Тип | Описание | Примеры |
|-----|----------|---------|
| **Бизнес-домены** | Описание бизнес-областей и сущностей | `01-user-management.md`, `02-community-management.md` |
| **UI-спецификации** | Управление состоянием, взаимодействие | `07-ui-state-persistence.md` |
| **Технические** | API, интеграции, инфраструктура | `08-technical-specs.md` |
| **Концептуальные** | Общая концепция, глоссарий | `00-overview.md` |

### 4. Управление статусами

| Статус | Описание | Действия |
|--------|----------|----------|
| **Черновик** | Инициальное описание | Можно редактировать без согласования |
| **На обсуждении** | Требует проверки | Обсуждение с командой/пользователем |
| **Согласовано** | Утверждено | Начало разработки |
| **В реализации** | Разрабатывается | Обновление по мере прогресса |
| **Завершено** | Реализовано и проверено | Финальная версия |

### 5. Формат описания требований

- **FR (Functional Requirement)** — функциональные требования (что система делает)
- **NFR (Non-Functional Requirement)** — нефункциональные требования (как система работает)
- **Критерии приёмки** — проверяемые условия выполнения требования

## Процесс создания новой спецификации

1. **Анализ требования**
   - Определить бизнес-цель
   - Выявить связанные сущности
   - Определить границы функциональности

2. **Выбор домена**
   - Определить, к какому домену относится функциональность
   - Если домена нет — согласовать новый

3. **Создание спецификации**
   - Использовать утверждённый шаблон
   - Описать функциональные и нефункциональные требования
   - Указать связанные сущности

4. **Согласование**
   - Установить статус "На обсуждении"
   - Обсудить с командой/пользователем

5. **Утверждение**
   - Изменить статус на "Согласовано"
   - Начать разработку

6. **Мониторинг**
   - Обновлять статус при изменении
   - Фиксировать изменения в истории версий
