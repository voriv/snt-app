# US-07: Реализация процесса регистрации

**Родительский Epic:** `REQ-AUTH-001: Аутентификация и регистрация`  
**Дата создания:** 2026-07-10  
**Статус:** [To Do]

## 📋 Описание User Story

**Как** новый пользователь,  
**Я хочу** заполнять форму регистрации и проходить проверку данных,  
**Чтобы** получить учётную запись и роль GUEST.

---

## 🎯 Контекст

### Проблема
- Пользователь зашёл на страницу регистрации, но нет серверной логики для создания учётной записи
- Форма отправляет данные, но ничего не происходит
- Отсутствует обработка ошибок при создании пользователя

### Решение
- Реализовать бэкенд API для регистрации пользователей
- Добавить валидацию данных на сервере
- Автоматически назначать роль GUEST при успешной регистрации
- Возвращать корректные сообщения об ошибках

### Границы
- ✅ Входит: API endpoint, валидация, создание пользователя в БД, назначение роли
- ❌ Не входит: UI формы (реализован в US-06), отправка email (future)

---

## 📜 Функциональные требования

### FR-REQ-AUTH-007-01: API endpoint для регистрации
Система должна предоставлять POST endpoint `/api/v1/auth/register` для создания новой учётной записи.

#### AC-7.1.1: POST /api/v1/auth/register
- **Дано:** Пользователь отправляет POST запрос с email, password, confirmPassword
- **Когда:** Система получает валидный запрос
- **Тогда:** 
  - Создается новый пользователь в БД
  - Автоматически назначается роль GUEST
  - Возвращается 201 Created с данными пользователя

#### AC-7.1.2: Валидация входных данных
- **Дано:** Пользователь отправляет данные регистрации
- **Когда:** Данные содержат ошибки
- **Тогда:** Система возвращает 400 Bad Request с описанием ошибок

---

### FR-REQ-AUTH-007-02: Валидация данных на сервере
Система должна валидировать все поля перед созданием пользователя.

#### AC-7.2.1: Валидация email
- **Дано:** Пользователь вводит email
- **Когда:** Email не соответствует формату
- **Тогда:** Возвращается ошибка с сообщением о некорректном формате

#### AC-7.2.2: Валидация email на уникальность
- **Дано:** Пользователь пытается зарегистрироваться с уже существующим email
- **Когда:** Email уже используется в системе
- **Тогда:** Возвращается 409 Conflict с сообщением о дубликате

#### AC-7.2.3: Валидация пароля
- **Дано:** Пользователь вводит пароль
- **Когда:** Пароль короче 6 символов
- **Тогда:** Возвращается ошибка валидации

#### AC-7.2.4: Проверка совпадения паролей
- **Дано:** Пользователь вводит пароль и подтверждение
- **Когда:** Пароли не совпадают
- **Тогда:** Возвращается ошибка о несоответствии

#### AC-7.2.5: Обработка пустых полей
- **Дано:** Пользователь заполняет не все обязательные поля
- **Когда:** Отправляется форма с пустыми полями
- **Тогда:** Возвращается ошибка с указанием каких полей не хватает

---

### FR-REQ-AUTH-007-03: Автоматическое назначение роли
Система должна автоматически назначать роль GUEST новому пользователю.

#### AC-7.3.1: Создание записи в UserRole
- **Дано:** Пользователь успешно зарегистрирован
- **Когда:** Создаётся запись в таблице UserRole
- **Тогда:** 
  - user_id указывает на созданного пользователя
  - role_id указывает на роль GUEST
  - created_at устанавливается автоматически

## ⚖️ Бизнес-правила (Business Rules)

| ID | Правило | Описание | Валидация |
|----|---------|----------|-----------|
| **BR-01** | Email должен быть уникальным | Система не допускает регистрации с уже существующим email | Проверка в БД перед созданием |
| **BR-02** | Пароль должен содержать минимум 6 символов | Защита от слишком слабых паролей | Валидация на сервере |
| **BR-03** | Подтверждение пароля должно совпадать с паролем | Гарантия что пользователь правильно ввёл пароль | Сравнение двух полей |
| **BR-04** | Новый пользователь получает роль GUEST | Автоматическое присвоение минимального уровня доступа | После успешной регистрации |
| **BR-05** | Email приводится к нижнему регистру | Унификация хранения email | При сохранении в БД |

## 🚨 Исключения и Граничные случаи (Edge Cases)

| # | Ситуация | Ожидаемое поведение |
|---|----------|---------------------|
| 1 | Email уже существует | Возврат 409 Conflict с сообщением "Пользователь с таким email уже существует" |
| 2 | Email невалидный | Возврат 400 Bad Request с сообщением "Некорректный формат email" |
| 3 | Пароль короче 6 символов | Возврат 400 Bad Request с сообщением "Пароль должен содержать минимум 6 символов" |
| 4 | Пароли не совпадают | Возврат 400 Bad Request с сообщением "Пароли не совпадают" |
| 5 | Пустые обязательные поля | Возврат 400 Bad Request с перечнем отсутствующих полей |
| 6 | Email с разными регистрами | Оба email 'Test@example.com' и 'test@example.com' считаются одинаковыми |
| 7 | Пробелы вокруг email | Пробелыtrimмируются перед валидацией |

## 🔐 Нефункциональные требования (NFR)

### Безопасность
- **NFR-01:** Пароли должны хешироваться перед сохранением (bcrypt)
- **NFR-02:** Не передавать пароли в ответе API
- **NFR-03:** Все ошибки должны иметь общий формат, без разглашения внутренней структуры

### Производительность
- **NFR-04:** Время отклика API ≤ 500ms при нормальных условиях
- **NFR-05:** Проверка уникальности email не должна блокировать более 100ms

### Доступность (A11y)
- **NFR-06:** Ошибки должны быть доступны скринридерам (aria-live)

### Локализация
- **NFR-07:** Все сообщения об ошибках на русском языке
