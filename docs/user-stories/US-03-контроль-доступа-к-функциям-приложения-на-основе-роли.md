# US-03: Контроль доступа к функциям приложения на основе роли

---

## Формулировка

**Как** администратор СНТ,
**я хочу** чтобы система проверяла мою роль перед выполнением функций приложения,
**чтобы** я не мог выполнять операции, недоступные для моей роли.

---

## Целевое состояние

Система реализует централизованный механизм защиты функций приложения через декоратор/обёртку `withRoleGuard`, которая применяется к API Route Handlers. Перед выполнением handler'а система проверяет роль пользователя на основе access_type endpoint'а:
- `public` — доступ без ограничений (только авторизация)
- `owner` — доступ для владельца ресурса
- `super_admin` — только для роли SUPER_ADMIN
- `role` — доступ для пользователей с назначенными правами в `role_api_endpoints`

Если проверка доступа не проходит, система возвращает HTTP 403 Forbidden с сообщением на русском языке "Доступ запрещён". Проверка выполняется на уровне сервера, что гарантирует безопасность данных даже при прямом вызове API без клиентской защиты.

## Модель данных

| Сущность | Описание | Ссылка на модель |
|----------|----------|------------------|
| ApiEndpoint | Регистр API endpoints с полями: path, method, access_type, isActive | `docs/model/entities/api-endpoint.md` |
| RoleApiEndpoint | Связующая таблица M:N между ролями и API endpoints | `docs/model/entities/role-api-endpoint.md` |
| Role | Роли системы: GUEST, MEMBER, ADMIN, SUPER_ADMIN | `docs/model/entities/role.md` |
| User | Пользователи системы | `docs/model/entities/user.md` |

### Ключевые инварианты модели

- `access_type` endpoint'а определяет уровень защиты: `public`, `owner`, `super_admin`, `role`
- Комбинация (`role_id`, `api_endpoint_id`) уникальна в `role_api_endpoints`
- SUPER_ADMIN имеет привилегированный доступ через runtime-правило (без необходимости записи в `role_api_endpoints`)

---

## Поведение (User Behavior)

### B-1: Проверка доступа пользователя к API endpoint

Пользователь делает запрос к защищённому API endpoint'у. Middleware/обёртка `withRoleGuard` извлекает userId из сессии, проверяет доступ через `AccessService.canAccessApi`. Если доступ разрешён — выполняется handler, иначе возвращается 403 Forbidden.

### B-2: Попытка доступа пользователя без необходимых прав

Пользователь с ролью MEMBER пытается вызвать endpoint с `access_type=super_admin` или endpoint, к которому у него нет прав в `role_api_endpoints`. `AccessService.canAccessApi` возвращает false, `withRoleGuard` возвращает HTTP 403 Forbidden.

### B-3: Запрос к endpoint с access_type=public

Пользователь делает запрос к endpoint'у с `access_type=public`. Проверка доступа пропускается (только авторизация через Middleware), handler выполняется без дополнительных проверок ролей.

## Критерии приёмки

### AC-1: Проверка доступа к endpoint с access_type=role

- **Given** у пользователя есть роль MEMBER, но нет назначенных прав в `role_api_endpoints` для endpoint `/api/v1/roles`
- **When** пользователь делает POST запрос к `/api/v1/roles`
- **Then** система возвращает HTTP 403 Forbidden с сообщением "Доступ запрещён"

### AC-2: Доступ SUPER_ADMIN ко всем endpoint'ам

- **Given** пользователь имеет роль SUPER_ADMIN
- **When** пользователь делает запрос к любому API endpoint'у (включая `/api/v1/roles`)
- **Then** система возвращает HTTP 200/201 (handler выполняется успешно)

### AC-3: Проверка доступа через role_api_endpoints

- **Given** у пользователя есть роль MEMBER и в `role_api_endpoints` есть запись для этой роли и endpoint `/api/v1/members`
- **When** пользователь делает POST запрос к `/api/v1/members`
- **Then** система возвращает HTTP 201 Created (доступ разрешён)

### AC-4: Неавторизованный доступ к endpoint

- **Given** пользователь не авторизован (отсутствует сессия)
- **When** пользователь делает запрос к любому API endpoint'у
- **Then** система возвращает HTTP 401 Unauthorized (проверка на уровне Middleware)

### AC-5: Endpoint с access_type=public доступен без роли

- **Given** endpoint имеет `access_type=public`
- **When** авторизованный пользователь делает запрос к этому endpoint'у
- **Then** система выполняет handler без дополнительных ролевых проверок

## Бизнес-правила и валидация

| ID | Правило | Валидация |
|----|---------|-----------|
| BR-04 | Доступ к функциям приложения контролируется на основе роли пользователя | Runtime: `AccessService.canAccessApi()` проверяет access_type endpoint'а и роль пользователя |
| BR-06 | Роли хранятся в системе и ассоциируются с пользователями | DB Constraint: таблица `user_roles` с составным PK (`user_id`, `role_id`) |
| BR-19 | SUPER_ADMIN имеет привилегированный доступ ко всем функциям приложения | Runtime-правило в `AccessService`: при наличии роли SUPER_ADMIN → true (без обращения к `role_api_endpoints`) |
| BR-20 | Endpoint'ы с `access_type=role` требуют назначения прав через `role_api_endpoints` | Проверка наличия записи в `role_api_endpoints` для любой роли пользователя |

### Примеры валидаций

- **Проверка SUPER_ADMIN (BR-19):** `AccessService.canAccessApi()` проверяет наличие роли SUPER_ADMIN через `findRolesByUserId(userId)`, возвращает true без обращения к `role_api_endpoints`
- **Проверка role (BR-20):** Для access_type=role проверяется наличие записи в `role_api_endpoints` для любой роли пользователя через `findRolesByEndpointId(endpoint.id)`

## Граничные случаи (Edge Cases)

| # | Ситуация | Ожидаемое поведение |
|---|----------|---------------------|
| 1 | Неавторизованный доступ к функциям (отсутствует сессия) | 401 Unauthorized (Middleware next-auth) |
| 2 | Пользователь без необходимых прав (role=MEMBER, нет записи в role_api_endpoints) | 403 Forbidden с сообщением "Доступ запрещён" |
| 3 | Сессия истекла (недействительный токен) | 401 Unauthorized (Middleware next-auth) |
| 4 | Endpoint с access_type=public, пользователь не авторизован | 401 Unauthorized (Middleware требует авторизации для всех API) |
| 5 | Endpoint не найден в реестре api_endpoints | 403 Forbidden (endpoint считается недоступным) |
| 6 | Endpoint is_active=false | 403 Forbidden (неактивные endpoint'ы недоступны для всех, включая SUPER_ADMIN) |
| 7 | Пользователь имеет несколько ролей, одна из которых имеет права | 200/201 (доступ разрешён через любую роль) |
| 8 | Сбой БД при проверке ролей | 500 Internal Server Error (ошибка сервиса) |

## Нефункциональные требования

- **Производительность:** Проверка доступа < 50ms (загрузка endpoint'ов + проверка ролей через БД)
- **Безопасность:**
  - Проверка доступа выполняется строго на сервере
  - Клиент не может обогнуть проверку через модификацию запросов
  - SUPER_ADMIN имеет привилегированный доступ через runtime-правило
  - Неактивные endpoint'ы (is_active=false) недоступны для всех, включая SUPER_ADMIN
- **UX:** Сообщения об ошибках на русском языке, понятные пользователю ("Доступ запрещён")
- **Надёжность:** Транзакционные проверки на уровне БД (если требуется)

## Открытые вопросы

| # | Вопрос | Допущение |
|---|--------|-----------|
| 1 | Должен ли `withRoleGuard` проверять авторизацию (сессию) или это задача Middleware? | Предварительное решение: авторизацию проверяет Middleware (EC-4), `withRoleGuard` проверяет только роли для уже авторизованных пользователей |
| 2 | Как обрабатывать endpoint'ы с динамическими параметрами (например, `/members/abc123`)? | Предварительное решение: сопоставление через `matchPath()` из `path-matcher.ts`, который поддерживает :param сегменты |
| 3 | Нужно ли логировать попытки несанкционированного доступа? | Предварительное решение: логирование в процессе разработки (console.warn), в продакшене — через внешнюю систему мониторинга |
