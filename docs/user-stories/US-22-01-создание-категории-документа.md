# US-22-01: Создание категории документа

> Эпик: Управление документами (REQ-DOCS-001)

---

## Формулировка

**Как** администратор СНТ,
**я хочу** создавать категории для документов с возможностью указания родительской категории,
**чтобы** организовать иерархическую структуру хранения документов.

---

## Целевое состояние

После реализации администратор сможет на странице `/dashboard/documents/categories` создать категорию, указав название, описание (опционально) и родительскую категорию (опционально — для создания подкатегории). Категория отображается в дереве категорий на странице управления документами. Валидация выполняется на стороне клиента (Zod) и сервера.

---

## Модель данных

| Сущность | Описание | Ссылка на модель |
|----------|----------|------------------|
| DocumentCategory | Категория/подкатегория документов; поддержка иерархии через self-reference (parentId) | Будет создана |

### Ключевые поля сущности DocumentCategory
- `id` — varchar (PK, cuid)
- `name` — varchar(100), not null
- `description` — varchar(500), optional
- `parentId` — varchar, optional, self-ref → DocumentCategory.id
- `createdAt` — timestamp
- `updatedAt` — timestamp

---

## Поведение (User Behavior)

### B-1: Создание корневой категории
Администратор открывает страницу управления категориями (`/dashboard/documents/categories`), нажимает «Создать категорию», заполняет название и описание, оставляет поле «Родительская категория» пустым. Система валидирует ввод и сохраняет категорию как корневую (parentId = null). Администратор видит новую категорию в дереве категорий.

### B-2: Создание подкатегории
Администратор нажимает «Создать категорию», выбирает из выпадающего списка существующую родительскую категорию, заполняет название и описание. Система валидирует ввод и сохраняет категорию с parentId = выбранная категория. Новая подкатегория отображается вложенной под родительской в дереве категорий.

---

## Критерии приёмки

### AC-1: Успешное создание корневой категории
- **Given** администратор авторизован и находится на странице создания категории
- **When** администратор вводит название «Договоры» и нажимает «Сохранить» без выбора родительской категории
- **Then** система создаёт корневую категорию «Договоры» (parentId = null) и отображает её в списке категорий

### AC-2: Успешное создание подкатегории
- **Given** существует корневая категория «Договоры»
- **When** администратор создаёт подкатегорию «Договоры аренды» с родителем «Договоры»
- **Then** система создаёт категорию «Договоры аренды» с parentId = id категории «Договоры»

### AC-3: Валидация пустого названия
- **Given** администратор открыл форму создания категории
- **When** администратор оставляет поле «Название» пустым и нажимает «Сохранить»
- **Then** система отображает ошибку валидации «Название категории обязательно»

### AC-4: Уникальность названия в рамках одного родителя
- **Given** существует категория «Договоры» (корневая)
- **When** администратор пытается создать категорию «Договоры» (корневую)
- **Then** система возвращает ошибку «Категория с таким названием уже существует на этом уровне»

### AC-5: Валидация несуществующей родительской категории
- **Given** администратор заполняет форму создания категории
- **When** администратор указывает parentId несуществующей категории
- **Then** система возвращает ошибку «Родительская категория не найдена»

## Бизнес-правила и валидация

| ID | Правило | Валидация |
|----|---------|-----------|
| BR-03 | Категория может быть вложенной (подкатегория) или корневой | DB: self-reference parentId; Runtime: проверка существования parentId |
| BR-10 | Типы документов могут быть расширены без изменения кода | CRUD-категории через UI, не enum |

### Примеры валидаций
- **Название обязательно**: Zod schema — `name: z.string().min(1).max(100)`
- **Уникальность на уровне родителя**: уникальный составной индекс (name, parentId) — `@@unique([name, parentId])`; parentId = null считается отдельным уровнем (корневые категории)
- **Описание опционально**: `description: z.string().max(500).optional()`
- **Существование parentId**: проверка в сервисе перед созданием

## Граничные случаи (Edge Cases)

| # | Ситуация | Ожидаемое поведение |
|---|----------|---------------------|
| 1 | Название категории превышает 100 символов | Система отклоняет с ошибкой «Название категории не должно превышать 100 символов» |
| 2 | Название содержит только пробелы | Система отклоняет как пустое название (trim перед валидацией) |
| 3 | Специальные символы / XSS в названии | Zod-схема экранирует/отсекает опасные символы |
| 4 | Одновременное создание двух категорий с одинаковым названием на одном уровне | Второй запрос получает ошибку уникальности (Prisma P2002 → понятное сообщение) |
| 5 | Создание категории при отсутствии соединения с БД | Система возвращает 500 с сообщением «Ошибка сервера. Попробуйте позже.» |
