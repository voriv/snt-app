# US-21-24: Выдача предупреждения пользователю

## Формулировка
**Как** модератор,
**я хочу** выдавать предупреждения пользователям за незначительные нарушения,
**чтобы** предупредить их о недопустимости подобных действий и избежать более строгих мер.

## Целевое состояние
Модератор может выдать предупреждение пользователю с указанием причины и типа нарушения. Пользователь получает уведомление о предупреждении, и оно записывается в историю нарушений.

### Границы
- Предупреждение доступно только модераторам и супер-администраторам.
- Предупреждение не блокирует пользователя, но влияет на его репутацию.
- Предупреждение должно иметь причину и тип нарушения.
- Пользователь получает уведомление о предупреждении.
- Количество предупреждений может влиять на автоматические меры (например, 3 предупреждения = 24ч блокировка).

## Функциональные требования

### FR-REQ-COMMS-001-24: Выдача предупреждения пользователю

#### AC-24.1: Выдача предупреждения с указанием причины
- **Дано:** Модератор находится на странице карточки пользователя или видит кнопку "Выдать предупреждение".
- **Когда:** Модератор нажимает "Выдать предупреждение", выбирает тип нарушения, вводит причину и подтверждает.
- **Тогда:**
  - Пользователю записывается предупреждение в историю нарушений.
  - Пользователь получает уведомление о предупреждении.
  - Общее количество предупреждений пользователя увеличивается.
  - Модератор видит уведомление "Предупреждение выдано".

#### AC-24.2: Выбор типа нарушения
- **Дано:** Модератор выдает предупреждение.
- **Когда:** Модератор выбирает тип нарушения из списка (Спам, Неприемлемый контент, Харассмент, Другое).
- **Тогда:**
  - Тип нарушения записывается вместе с предупреждением.
  - В истории нарушений отображается тип нарушения.

#### AC-24.3: Комментарий к предупреждению
- **Дано:** Модератор выдает предупреждение.
- **Когда:** Модератор вводит произвольный комментарий к предупреждению.
- **Тогда:**
  - Комментарий сохраняется в истории нарушений.
  - Комментарий может быть отображен в уведомлении пользователя.

### FR-REQ-COMMS-001-25: Ведение истории предупреждений
- **Дано:** Пользователь имеет выданные предупреждения.
- **Когда:** Модератор открывает карточку пользователя или страницу истории предупреждений.
- **Тогда:**
  - Отображается chronological-список предупреждений: дата, тип, причина, модератор, комментарий.
  - Отображается общее количество активных предупреждений.

### FR-REQ-COMMS-001-26: Автоматические меры при накоплении предупреждений
- **Дано:** Пользователь накопил определенное количество предупреждений (например, 3).
- **Когда:** Модератор выдает предупреждение, которое приводит пользователя к порогу.
- **Тогда:**
  - Система автоматически применяет дополнительные меры (например, временная блокировка на 24ч).
  - Пользователь получает уведомление о новой мере.

## Бизнес-правила и валидация

| ID | Правило | Описание | Валидация |
|----|---------|----------|-----------|
| BR-24-01 | Право модератора | Выдавать предупреждения может модератор/SUPER_ADMIN. | Проверка роли в API. |
| BR-24-02 | Тип нарушения обязателен | Предупреждение должно иметь тип нарушения. | Валидация `violationType` как обязательного поля. |
| BR-24-03 | Комментарий обязателен | Предупреждение должно иметь причину/комментарий. | Валидация `comment` как обязательного поля. |
| BR-24-04 | Лимит активных предупреждений | Активные предупреждения хранятся определенный срок (например, 90 дней). | Проверка даты создания предупреждения. |
| BR-24-05 | Автоматические меры | При достижении порога предупреждений применяются автоматические меры. | Проверка количества активных предупреждений при выдаче. |

## Граничные случаи (Edge Cases)

| # | Ситуация | Ожидаемое поведение |
|---|----------|---------------------|
| 1 | Выдача предупреждения пользователю, у которого уже есть максимальное количество активных предупреждений | Предупреждение записывается, но не влияет на автоматические меры (сгорает старое). |
| 2 | Выдача предупреждения пользователю, который заблокирован | Предупреждение записывается, но пользователь не получит уведомление (будет после разблокировки). |
| 3 | Выдача предупреждения пользователю, который не существует | Операция отклоняется с ошибкой 404. |
| 4 | Выдача предупреждения во время сетевого сбоя | Операция не выполняется, пользователь получает ошибку "Не удалось выдать предупреждение". |
| 5 | Накопление предупреждений до порога автоматической блокировки | Автоматическая блокировка применяется сражу после выдачи предупреждения. |
| 6 | Выдача предупреждения за то же нарушение несколько раз подряд | Каждое предупреждение записывается отдельно, но система может учитывать повторные нарушения. |

## Модель данных
Создание таблицы `UserWarning` для хранения предупреждений.

**Таблица: `user_warnings`**
| Поле | Тип | Описание |
|------|-----|----------|
| `id` | UUID | Primary Key |
| `user_id` | UUID | Foreign Key -> users(id) |
| `moderator_id` | UUID | Foreign Key -> users(id) (модератор) |
| `violation_type` | String | Тип нарушения (Спам, Харассмент, и т.д.) |
| `reason` | Text | Причина/комментарий |
| `created_at` | DateTime | Дата выдачи |
| `expires_at` | DateTime | Дата истечения (опционально, например, через 90 дней) |

**Обновление таблицы `users`:**
```prisma
model User {
  // ... другие поля
  warningCount    Int      @default(0) @map("warning_count")
  lastWarningAt   DateTime? @map("last_warning_at")
}
```

## Нефункциональные требования
- **Производительность:** Запрос истории предупреждений < 200мс.
- **Безопасность:** Проверка прав модератора на выдачу предупреждений.
- **Надежность:** Автоматические меры должны применяться надежно при достижении порога.
- **Аудит:** Все предупреждения должны записываться с указанием модератора и причины.
