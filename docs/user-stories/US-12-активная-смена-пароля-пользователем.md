# US-12: Активная смена пароля пользователем

**Родительский Epic:** `REQ-AUTH-001: Аутентификация и регистрация`
**Дата создания:** 2026-07-27
**Статус:** [To Do]
**Приоритет:** Medium
**Связанная задача:** B-015

---

## 📋 Описание User Story

**Как** авторизованный пользователь,
**Я хочу** сменить свой пароль, вводя текущий пароль, новый пароль и его подтверждение,
**Чтобы** поддерживать безопасность учётной записи.

---

## 🎯 Контекст

### Проблема
- Авторизованный пользователь не может сменить пароль в приложении
- Отсутствует API для обновления пароля
- Пользователь не может повысить безопасность учётной записи в случае компрометации

### Решение
- Реализовать API endpoint `PUT /api/v1/auth/password` для смены пароля
- Добавить серверную валидацию (Zod) для всех полей
- Реализовать проверку текущего пароля перед применением нового
- Реализовать бизнес-логику хеширования нового пароля (bcrypt)
- Создать UI страницу `/settings/security` с формой смены пароля
- Точки входа на форму: страница профиля (раздел `/settings/security`), ссылка из раздела профиля, модальное окно из выпадающего меню аватара

### Границы
- ✅ Входит: API endpoint, серверная валидация, проверка текущего пароля, хеширование нового пароля, UI страница `/settings/security`
- ❌ Не входит: восстановление пароля по email, инвалидация сессий при смене пароля (BR-11 — сессии сохраняются)

---

## 🎯 Бизнес-ценность

- **Безопасность:** пользователь может самостоятельно сменить пароль при подозрении на компрометацию
- **Соответствие:** требование безопасности для систем с персональными данными (152-ФЗ)
- **UX:** стандартная возможность, ожидаемая пользователями в современных веб-приложениях

---

## 📜 Функциональные требования

### FR-REQ-AUTH-009-01: API endpoint для смены пароля

Система должна предоставлять API endpoint `PUT /api/v1/auth/password` для смены пароля авторизованным пользователем.

#### AC-9.1: Успешная смена пароля
- **Given** авторизованный пользователь с существующим паролем
- **When** система получает `PUT /api/v1/auth/password` с телом `{ currentPassword: "СтарыйПароль123", newPassword: "НовыйПароль456", confirmPasswordNew: "НовыйПароль456" }` и все поля проходят валидацию
- **Then** новый пароль хешируется (bcrypt) и сохраняется в БД
- **Then** возвращается `200 OK` с `{ success: true }`
- **Then** существующие сессии пользователя сохраняются (BR-11)

#### AC-9.2: Неверный текущий пароль
- **Given** авторизованный пользователь
- **When** система получает запрос с неверным `currentPassword`
- **Then** возвращается `400 Bad Request` с сообщением «Неверный текущий пароль»
- **Then** пароль не изменяется

#### AC-9.3: Новый пароль совпадает с текущим
- **Given** авторизованный пользователь
- **When** система получает запрос, где `newPassword` совпадает с текущим паролем
- **Then** возвращается `400 Bad Request` с сообщением «Новый пароль не может совпадать с текущим»
- **Then** пароль не изменяется

#### AC-9.4: Валидация длины нового пароля
- **Given** авторизованный пользователь
- **When** система получает запрос, где `newPassword` короче 6 символов
- **Then** возвращается `400 Bad Request` с сообщением «Пароль должен содержать минимум 6 символов»
- **Then** пароль не изменяется

#### AC-9.5: Новый пароль и подтверждение не совпадают
- **Given** авторизованный пользователь
- **When** система получает запрос, где `newPassword` !== `confirmPasswordNew`
- **Then** возвращается `400 Bad Request` с сообщением «Пароли не совпадают»
- **Then** пароль не изменяется

#### AC-9.6: Вход с новым паролем после смены
- **Given** пользователь успешно сменил пароль
- **When** пользователь выходит из системы (US-08) и пытается войти с новым паролем через `POST /api/v1/auth/login`
- **Then** аутентификация проходит успешно, создаётся новая сессия
- **Then** при попытке входа со старым паролем возвращается ошибка «Неверный email или пароль»

---

### FR-REQ-AUTH-009-02: UI страница смены пароля

Система должна предоставлять UI страницу `/settings/security` с формой смены пароля.

#### AC-9.7: Отображение формы
- **Given** авторизованный пользователь находится на странице `/settings/security`
- **When** страница загружается
- **Then** отображается форма с тремя полями: «Текущий пароль», «Новый пароль», «Подтверждение нового пароля»
- **Then** все поля обязательны для заполнения
- **Then** кнопка отправки «Сменить пароль» неактивна, пока не заполнены все поля

#### AC-9.8: Успешная отправка формы
- **Given** авторизованный пользователь заполнил форму валидными данными
- **When** пользователь нажимает «Сменить пароль»
- **Then** отправляется `PUT /api/v1/auth/password`
- **Then** отображается уведомление об успешной смене пароля
- **Then** поля формы очищаются

#### AC-9.9: Ошибка валидации на клиенте
- **Given** авторизованный пользователь заполняет форму
- **When** новый пароль содержит менее 6 символов или пароли не совпадают
- **Then** отображается клиентская ошибка валидации до отправки на сервер

#### AC-9.10: Ошибка от сервера
- **Given** авторизованный пользователь отправил форму
- **When** сервер возвращает ошибку (неверный текущий пароль, дублирование, и т.д.)
- **Then** отображается сообщение об ошибке под соответствующим полем или в общей области уведомлений
- **Then** введённые данные (кроме текущего пароля) сохраняются в форме

#### AC-9.11: Защита маршрута
- **Given** неавторизованный пользователь
- **When** пользователь пытается открыть `/settings/security`
- **Then** выполняется редирект на страницу входа `/login` (US-NAV-01)

#### AC-9.12: Состояние загрузки
- **Given** авторизованный пользователь отправил форму
- **When** ожидается ответ от сервера
- **Then** кнопка «Сменить пароль» показывает индикатор загрузки
- **Then** все поля формы заблокированы до получения ответа

---

### FR-REQ-AUTH-009-03: Навигация к странице смены пароля

Система должна предоставлять несколько способов доступа к странице смены пароля.

#### AC-9.13: Доступ через навигацию
- **Given** авторизованный пользователь
- **When** пользователь открывает страницу профиля `/dashboard/profile` или выпадающее меню аватара
- **Then** присутствует ссылка «Безопасность» или «Сменить пароль», ведущая на `/settings/security`

## ⚖️ Бизнес-правила (Business Rules)

| ID | Правило | Описание | Валидация |
|----|---------|----------|-----------|
| **BR-08** | Подтверждение текущего пароля | Для смены пароля требуется ввод корректного текущего пароля (защита от несанкционированной смены) | `bcrypt.compare(currentPassword, storedHash)` |
| **BR-09** | Новый пароль ≠ текущему | Новый пароль не может совпадать с текущим | Сравнение `bcrypt.compare(newPassword, storedHash)` после проверки текущего пароля |
| **BR-10** | Минимальная длина пароля | Новый пароль: минимум 6 символов | Zod: `z.string().min(6, 'Пароль должен содержать минимум 6 символов')` |
| **BR-11** | Сохранение сессий | При успешной смене пароля все активные сессии пользователя сохраняются (не инвалидируются) — так как смена инициирована самим пользователем | Нет — логика NextAuth: сессии остаются валидными |
| **BR-12** | Хеширование паролей | Пароли хранятся только в зашифрованном виде (bcrypt) | `bcrypt.hash(newPassword, 10)` перед сохранением |

## 🚨 Исключения и Граничные случаи (Edge Cases)

| # | Ситуация | Ожидаемое поведение |
|---|----------|---------------------|
| **EC-06** | Текущий пароль неверный | Возврат ошибки «Неверный текущий пароль» (HTTP 400) |
| **EC-07** | Новый пароль совпадает с текущим | Возврат ошибки «Новый пароль не может совпадать с текущим» (HTTP 400) |
| **EC-08** | Новый пароль менее 6 символов | Возврат ошибки валидации «Пароль должен содержать минимум 6 символов» (HTTP 400) |
| **EC-09** | Новый пароль и подтверждение не совпадают | Возврат ошибки «Пароли не совпадают» (HTTP 400) |
| 10 | Пустые поля в запросе | Возврат ошибки валидации с перечнем отсутствующих полей (HTTP 400) |
| 11 | Неавторизованный запрос к API | Возврат `401 Unauthorized`; UI редирект на `/login` |
| 12 | Сессия истекла во время заполнения формы | При отправке — `401`; редирект на `/login` с сохранением `callbackUrl` |
| 13 | Сетевая ошибка при отправке | Отображение уведомления «Ошибка сети. Попробуйте позже»; данные формы сохраняются |
| 14 | Некорректный формат нового пароля (невалидные символы) | Возврат ошибки валидации с конкретным описанием |
| 15 | Попытка смены пароля деактивированным пользователем | Возврат `403 Forbidden` (пользователь заблокирован) |

## 🔐 Нефункциональные требования (NFR)

### Безопасность
- **NFR-01:** Пароли передаются только в теле запроса (не в URL, не в заголовках)
- **NFR-02:** Пароли никогда не возвращаются в ответе API
- **NFR-03:** Хеширование нового пароля через bcrypt (cost factor ≥ 10)
- **NFR-04:** Сообщения ошибок не раскрывают причину отказа (единое сообщение для неверного пароля) — см. EC-06
- **NFR-05:** Защита от CSRF (через встроенный механизм NextAuth)

### Производительность
- **NFR-06:** Время отклика API ≤ 500ms (включая хеширование bcrypt)

### UX
- **NFR-07:** Сообщения об ошибках на русском языке
- **NFR-08:** Валидация в реальном времени на клиенте (при вводе)
- **NFR-09:** Поля пароля имеют кнопку «показать/скрыть» пароль (глазик)
- **NFR-10:** Все поля доступны с клавиатуры (tab order: текущий → новый → подтверждение → кнопка)
- **NFR-11:** Ошибки доступны скринридерам (aria-live, aria-describedby)
- **NFR-12:** Кнопка отправки деактивирована во время загрузки (предотвращение двойной отправки)
