# US-22-04: Назначение метаданных при загрузке

> Эпик: Управление документами (REQ-DOCS-001)

---

## Формулировка

**Как** администратор СНТ,
**я хочу** заполнять метаданные (название, описание, категория, тип, теги, видимость по ролям) при загрузке документа,
**чтобы** документ был правильно классифицирован и доступен нужным пользователям.

---

## Целевое состояние

После реализации администратор, загрузив файл (US-22-03), переходит на шаг назначения метаданных. Форма содержит поля: название (обязательно), описание (опционально), категория (выбор из дерева), тип документа (выбор из списка), теги (множественный выбор / ввод), видимость по ролям (чекбоксы: GUEST, MEMBER, ADMIN). После сохранения документ получает статус `published` и становится видимым пользователям с соответствующими ролями.

---

## Модель данных

| Сущность | Описание | Ссылка на модель |
|----------|----------|------------------|
| Document | Основные метаданные | Будет создана |
| DocumentCategory | Категория | Будет создана |
| DocumentTag | Теги (связь M:N Document ↔ Tag) | Будет создана |

### Ключевые поля сущности Document (для метаданных)
- `title` — varchar(255), not null (отображаемое название)
- `description` — text, optional
- `categoryId` — varchar, optional, ref → DocumentCategory.id
- `documentType` — varchar(50), not null (например: «Договор», «Протокол», «Справка»)
- `visibleRoles` — varchar[] (JSON array), not null, default: ['ADMIN']
- `status` — varchar, default: 'draft' → 'published' после сохранения метаданных

### Ключевые поля сущности DocumentTag
- `id` — varchar (PK, cuid)
- `name` — varchar(50), unique, not null

### Связь Document ↔ DocumentTag
- `document_tags` — junction table (document_id, tag_id)

---

## Поведение (User Behavior)

### B-1: Заполнение метаданных после загрузки файла
Администратор загружает файл (US-22-03) и автоматически переходит на форму метаданных. Заполняет название «Протокол общего собрания 01.03.2025», выбирает категорию «Протоколы», тип «Протокол», назначает теги «2025», «Собрание», устанавливает видимость: MEMBER + ADMIN. Нажимает «Сохранить». Документ публикуется.

### B-2: Публикация с ограниченной видимостью
Администратор загружает внутренний документ и устанавливает видимость только для ADMIN. Документ сохраняется в статусе published, но виден только администраторам.

---

## Критерии приёмки

### AC-1: Успешное заполнение всех метаданных
- **Given** администратор загрузил файл (запись Document со статусом draft существует)
- **When** администратор заполняет: название «Протокол», категория «Протоколы», тип «Протокол», теги «2025», «Собрание», видимость [MEMBER, ADMIN] и нажимает «Сохранить»
- **Then** метаданные сохраняются; статус → published; документ виден пользователям с ролями MEMBER и ADMIN

### AC-2: Валидация пустого названия
- **Given** администратор открыл форму метаданных
- **When** оставляет поле «Название» пустым
- **Then** система отображает ошибку «Название документа обязательно»

### AC-3: Документ с ограниченной видимостью
- **Given** администратор установил видимость [ADMIN]
- **When** пользователь с ролью MEMBER запрашивает список документов
- **Then** этот документ в списке не отображается

### AC-4: Привязка тегов к документу
- **Given** администратор указал теги «2025», «Собрание»
- **When** сохраняет метаданные
- **Then** в junction table `document_tags` создаются связи Document ↔ Tag(2025), Document ↔ Tag(Собрание); новые теги создаются автоматически, если не существуют

### AC-5: Переход статуса draft → published
- **Given** документ в статусе draft после загрузки файла
- **When** администратор сохраняет метаданные
- **Then** статус документа меняется на published

## Бизнес-правила и валидация

| ID | Правило | Валидация |
|----|---------|-----------|
| BR-04 | Видимость привязывается к роли | DB: JSON array visibleRoles; Runtime: проверка при фильтрации |
| BR-06 | Статусы: draft, published, archived | DB: enum |
| BR-10 | Теги — настраиваемые | CRUD через US-22-07 |
| BR-11 | Поиск по тегам | Runtime: WHERE tags @> [...] |

### Примеры валидаций
- **Название обязательно**: `title: z.string().min(1).max(255)`
- **Тип документа**: `documentType: z.string().min(1).max(50)`
- **Категория**: `categoryId: z.string().uuid().optional()`
- **Видимость**: `visibleRoles: z.array(z.enum(['GUEST', 'MEMBER', 'ADMIN'])).min(1)`
- **Теги**: `tags: z.array(z.string().max(50)).max(10)`

## Граничные случаи (Edge Cases)

| # | Ситуация | Ожидаемое поведение |
|---|----------|---------------------|
| 1 | Сохранение метаданных без категории | categoryId = null; документ в «Без категории» |
| 2 | Указан несуществующий categoryId | Ошибка «Категория не найдена» |
| 3 | Видимость = пустой массив | Ошибка «Выберите хотя бы одну роль для доступа» |
| 4 | Тег не существует в БД | Авто-создание тега перед связыванием |
| 5 | Повторное сохранение метаданных | Обновление (PUT), не создание |
