# US-01: Автоматическое назначение роли GUEST при регистрации

---

## Формулировка

**Как** новый пользователь,
**я хочу** чтобы мне автоматически назначилась роль GUEST при регистрации,
**чтобы** я получил минимальный доступ к системе без дополнительных действий.

---

## Целевое состояние

После регистрации через существующий endpoint `/api/v1/auth/register` система автоматически создаёт запись о связи пользователя с системной ролью GUEST в рамках единой транзакции создания пользователя. Пользователь сразу получает минимальный набор прав, определённый для роли GUEST, и может взаимодействовать с системой (просмотр публичных разделов, доступных гостю страниц и функций) без ручного назначения роли администратором.

Назначение роли происходит прозрачно для пользователя — он не выполняет никаких дополнительных действий и не видит процесса назначения. Регистрация либо завершается полностью успешно (пользователь создан + роль GUEST назначена), либо полностью откатывается — частичное состояние (пользователь без роли) недопустимо.

---

## Модель данных

| Сущность | Описание | Ссылка на модель |
|----------|----------|------------------|
| User | Пользователь системы, создаваемый при регистрации | `docs/model/entities/user.md` |
| Role | Системная роль GUEST (is_system=true), предустановленная в БД | `docs/model/entities/role.md` |
| UserRole | Связующая запись M:N между пользователем и ролью GUEST | `docs/model/entities/user-role.md` |

### Ключевые инварианты модели

- Комбинация (`user_id`, `role_id`) уникальна — роль GUEST назначается пользователю ровно один раз (составной PK в `user_roles`)
- Запись `UserRole` создаётся в той же транзакции, что и `User` — атомарность
- Роль GUEST должна существовать в таблице `roles` до момента регистрации (предустановлена через seed)

---

## Поведение (User Behavior)

### B-1: Успешная регистрация нового пользователя
Новый пользователь вводит email и пароль на странице регистрации и отправляет форму. Система валидирует данные, проверяет уникальность email, хеширует пароль, создаёт запись пользователя и в рамках той же транзакции находит системную роль GUEST и создаёт связку `UserRole`. Пользователь получает успешный ответ и может войти в систему с ролью GUEST.

### B-2: Регистрация при отсутствии роли GUEST в системе
Администратор или процесс инициализации не создал системную роль GUEST в таблице `roles`. При регистрации нового пользователя система не может найти роль GUEST — операция назначения пропускается или завершается ошибкой (см. EC-2, открытый вопрос OQ-1). Пользователь создаётся, но без роли, либо регистрация отклоняется.

## Критерии приёмки

### AC-1: Успешное автоматическое назначение роли GUEST
- **Given** в таблице `roles` существует системная роль с `name = 'GUEST'`
- **When** новый пользователь проходит регистрацию с валидными email и паролем
- **Then** в таблице `users` создаётся запись пользователя, и в таблице `user_roles` создаётся запись, связывающая этого пользователя с ролью GUEST

### AC-2: Атомарность создания пользователя и назначения роли
- **Given** процесс регистрации инициирован
- **When** создание пользователя и назначение роли выполняются
- **Then** обе операции выполняются в единой транзакции — при ошибке на любом шаге обе операции откатываются, частичное состояние «пользователь без роли» не сохраняется

### AC-3: Идемпотентность назначения роли
- **Given** у пользователя уже есть роль GUEST
- **When** повторно инициируется назначение роли GUEST этому же пользователю
- **Then** дублирующая запись `UserRole` не создаётся (нарушение составного PK), ошибка не пробрасывается пользователю

### AC-4: Регистрация без дублирования при повторной отправке
- **Given** пользователь уже зарегистрирован с email `test@example.com`
- **When** повторно отправляется запрос на регистрацию с тем же email
- **Then** система возвращает ошибку о дублировании email, новая запись пользователя и запись `UserRole` не создаются

### AC-5: Регистрация при отсутствии роли GUEST
- **Given** в таблице `roles` отсутствует роль с `name = 'GUEST'`
- **When** новый пользователь пытается зарегистрироваться
- **Then** система предотвращает создание пользователя без роли или возвращает ошибку регистрации (поведение определяется в OQ-1)

## Бизнес-правила и валидация

| ID | Правило | Валидация |
|----|----------|-----------|
| BR-02 | Новым пользователям автоматически назначается роль GUEST при регистрации | Runtime: создание записи `UserRole` в транзакции создания `User`; поиск роли по `name = 'GUEST'` |
| BR-01 | Система поддерживает три роли: GUEST, MEMBER, ADMIN | DB Constraint: предустановленные системные роли через seed |
| BR-06 | Роли хранятся в системе и ассоциируются с пользователями | DB Constraint: таблица `user_roles` с составным PK (`user_id`, `role_id`) |

### Примеры валидаций

- **Атомарность (BR-02):** создание `User` и `UserRole` выполняется через `prisma.$transaction` — при ошибке любого шага вся транзакция откатывается
- **Уникальность роли на пользователя:** составной PK (`user_id`, `role_id`) в `user_roles` гарантирует, что роль GUEST назначается пользователю один раз; повторная попытка создания записи вызывает Prisma P2002 и обрабатывается идемпотентно

## Граничные случаи (Edge Cases)

| # | Ситуация | Ожидаемое поведение |
|----|----------|---------------------|
| 1 | Пользователь без роли — автоматически назначается GUEST | При регистрации система проверяет и назначает роль GUEST в транзакции создания пользователя |
| 2 | Роль GUEST отсутствует в таблице `roles` | Регистрация предотвращается или откатывается — пользователь не создаётся без роли (см. OQ-1) |
| 3 | Одновременная регистрация двух пользователей с одним email | Один запрос завершается успешно, второй получает ошибку дублирования email (Prisma P2002 → UserDuplicateError); транзакция второго отката полностью |
| 4 | Сбой БД на шаге создания `UserRole` после создания `User` | Транзакция полностью откатывается — пользователь без роли не сохраняется |
| 5 | Повторный запрос регистрации с тем же email после успешной регистрации | Возврат ошибки UserDuplicateError; запись `UserRole` не дублируется |
| 6 | Сетевая ошибка во время запроса | Клиент отображает индикатор загрузки и сообщение об ошибке; серверная транзакция либо завершилась, либо откатилась — повторный запрос безопасен |

## Нефункциональные требования

- **Производительность:** Назначение роли GUEST не должно увеличивать время регистрации более чем на ~50ms (один дополнительный `SELECT` роли + один `INSERT` в `user_roles` в рамках транзакции)
- **Безопасность:**
  - Назначение роли GUEST выполняется сервером автоматически — пользователь не может влиять на назначаемую роль
  - Роль GUEST определяется по имени (`name = 'GUEST'`), а не по входным данным пользователя
  - Назначение происходит в транзакции — невозможно создать пользователя без роли (при условии существования GUEST)
- **UX:** Процесс прозрачен для пользователя — никаких дополнительных действий или уведомлений не требуется
- **Надёжность:** Атомарность через транзакцию БД гарантирует отсутствие «осиротевших» пользователей без роли
- **Локализация:** Сообщения об ошибках (при отсутствии роли GUEST) на русском языке
