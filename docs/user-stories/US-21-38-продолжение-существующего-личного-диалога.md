# US-21-38: Продолжение существующего личного диалога (запрет дублирования)

> Эпик: Система общения в СНТ (REQ-COMMS-004)

---

## Формулировка

**Как** зарегистрированный пользователь СНТ,
**я хочу** чтобы система не создавала новый личный диалог с пользователем, если такой диалог уже существует, а открывала существующий,
**чтобы** у меня не появлялось дублирующихся диалогов и я всегда попадал в один актуальный диалог с собеседником.

---

## Целевое состояние

Система гарантирует инвариант: между двумя пользователями существует не более одного активного личного диалога (type = `DIRECT`).

- **Backend:** При вызове `POST /api/v1/conversations` сервис `CommsService.startConversation()` проверяет существование личного диалога через `ICommsRepository.findConversationBetween(currentUserId, participantId)`. Если найден — возвращается `409 Conflict` с `{ conversationId, isNew: false }` и сообщением «Диалог с этим пользователем уже существует». Уникальность обеспечивается unique constraint в БД (защита от race condition: второй параллельный запрос получает 409).
- **Frontend:** На странице `/dashboard/comms/messages/new` для собеседников с существующим диалогом отображается кнопка «Открыть диалог» (вместо «Написать»). Клик — редирект на `/dashboard/comms/messages/:conversationId`. При получении `409` из API-клиента клиент извлекает `conversationId` и выполняет аналогичный редирект.

---

## Контекст

### Проблема

В текущей реализации (REQ-COMMS-001) отсутствует бизнес-правило, предотвращающее создание нескольких диалогов между одной и той же парой пользователей. Это ведёт к дублирующимся диалогам, затрудняет навигацию и дезориентирует пользователей.

### Решение

Добавить backend-валидацию (проверка существования + unique constraint) и согласованный UX на клиенте (кнопка «Открыть диалог», редирект в существующий диалог, обработка `409`).

### Границы

- **Входит в US:** backend-инвариант (проверка существования, unique constraint, ответ 409/201, метод `findConversationBetween`, race condition), frontend-UX открытия существующего диалога (кнопка «Открыть», редирект, обработка 409).
- **Явно исключено:** Создание диалога с пользователем, с которым ещё нет диалога (при наличии диалогов с другими пользователями) — US-21-39. Отправка сообщений (US-21-03). Блокировка пользователя (EC-02) и выбор самого себя (EC-01) — покрываются US-21-02. Групповые чаты.

## Функциональные требования

### FR-REQ-COMMS-004-01: Backend-проверка существования диалога

Система при создании личного диалога проверяет, существует ли уже диалог `type = DIRECT` между текущим пользователем и целевым.

#### AC-1: Попытка создать диалог, когда диалог уже существует

- **Дано:** Пользователь A уже имеет личный диалог (id = "conv-123") с Пользователем B
- **Когда:** Пользователь A вызывает `POST /api/v1/conversations` с `{ participantId: "B" }`
- **Тогда:** Сервер возвращает `409` с `{ conversationId: "conv-123", isNew: false }` и сообщением «Диалог с этим пользователем уже существует»

### FR-REQ-COMMS-004-05: Поиск диалога в репозитории

#### AC-2: `findConversationBetween` не зависит от порядка аргументов

- **Дано:** Существует диалог между пользователем A и B
- **Когда:** Вызывается `findConversationBetween(A, B)` или `findConversationBetween(B, A)`
- **Тогда:** Возвращается один и тот же диалог

### FR-REQ-COMMS-004-02: Ответ 409 с conversationId

#### AC-3: Возврат 409 при существующем диалоге

- **Дано:** Пользователь A имеет диалог (id = "conv-123") с Пользователем B
- **Когда:** Пользователь A вызывает `POST /api/v1/conversations` с `{ participantId: "B" }`
- **Тогда:** Сервер возвращает `409` с `{ conversationId: "conv-123", isNew: false }`

### FR-REQ-COMMS-004-06: Кнопка «Открыть диалог»

#### AC-4: Отображение кнопки «Открыть диалог» для существующего диалога

- **Дано:** Пользователь A заходит на `/dashboard/comms/messages/new` и имеет диалог с Пользователем B
- **Когда:** Страница загружает список пользователей
- **Тогда:** Рядом с Пользователем B отображается кнопка «Открыть диалог» (не «Написать»)

### FR-REQ-COMMS-004-07: Редирект в существующий диалог

#### AC-5: Переход в существующий диалог

- **Дано:** Рядом с Пользователем B отображается кнопка «Открыть диалог»
- **Когда:** Пользователь A кликает на кнопку
- **Тогда:** Происходит редирект на `/dashboard/comms/messages/:conversationId` существующего диалога

### FR-REQ-COMMS-004-08: Обработка 409 в API-клиенте

#### AC-6: Редирект при получении 409

- **Дано:** Пользователь кликает «Написать» до загрузки данных о существующих диалогах
- **Когда:** API возвращает `409` с `{ conversationId: "conv-123" }`
- **Тогда:** Клиент извлекает `conversationId` и редиректит на `/dashboard/comms/messages/conv-123`

## Бизнес-правила и валидация

| ID | Правило | Описание | Валидация |
|----|---------|----------|-----------|
| BR-01 | Один диалог на пару | Между двумя пользователями существует не более одного личного диалога (type = DIRECT) | Unique constraint в БД |
| BR-02 | Перенаправление в существующий | При попытке начать диалог с существующим — не создавать новый, а перенаправлять | Сервисная логика |
| BR-04 | Проверка на сервере | Проверка существования выполняется на backend для защиты от обхода API | Сервис + unique constraint |
| BR-05 | UX-отметка | Пользователи с существующим диалогом помечаются кнопкой «Открыть диалог» | Frontend |
| BR-06 | Unique constraint | Уникальность диалога обеспечивается unique constraint на комбинацию участников для DIRECT | DB constraint |

### Примеры валидаций
- **Unique constraint (BR-01/BR-06):** unique index на комбинацию участников для `type = DIRECT`, ловит конфликт при параллельных запросах (race condition).
- **Проверка на себя и блокировку** выполняется до поиска существующего (покрывается US-21-02).

## Граничные случаи (Edge Cases)

| # | Ситуация | Ожидаемое поведение |
|---|----------|---------------------|
| 1 | Два параллельных запроса на создание диалога с одним пользователем (race condition) | Первый создаёт диалог (201), второй получает 409 из-за unique constraint в БД |
| 2 | Пользователь открывает `/dashboard/comms/messages/new` и сразу кликает на пользователя до загрузки списка диалогов | Система выполняет API-запрос на создание, получает 409 и корректно редиректит в существующий диалог |
| 3 | Диалог был удалён администратором после отображения в списке | При попытке открыть диалог API возвращает 404, пользователь перенаправляется на страницу «Диалог не найден» |
| 4 | `findConversationBetween` вызван с аргументами в обратном порядке | Возвращается тот же диалог (порядок аргументов не важен) |

## Нефункциональные требования

- **Производительность:** Проверка существования диалога (`findConversationBetween`) должна выполняться за < 50 мс (индексированный запрос).
- **Безопасность:** Валидация на сервере обязательна — клиентскую проверку нельзя полагать единственной защитой.
- **Консистентность:** Инвариант «один диалог на пару» сохраняется даже при параллельных запросах (race condition предотвращается unique constraint в БД).
- **Доступность:** Кнопки «Написать» и «Открыть диалог» должны иметь различающиеся `aria-label` для скринридеров.
- **Локализация:** Сообщение «Диалог с этим пользователем уже существует» на русском языке.
