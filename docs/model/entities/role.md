# Role

## Описание

Настраиваемая роль системы — логический набор полномочий, предоставляющий доступ к страницам приложения. Роль связана с пользователями отношением M:N (один пользователь может иметь несколько ролей) и со страницами отношением M:N (одной роли можно назначить несколько страниц).

Системные роли (`is_system = true`) защищены от удаления и переименования. Системная роль `SUPER_ADMIN` обладает особым поведением: полный доступ ко всем страницам реализуется в коде проверки доступа (runtime-правило), а не через заполнение таблицы `role_pages`.

## Поля

| Поле | Тип | Обязательное | Описание | Бизнес-правила |
|------|-----|-------------|----------|----------------|
| `id` | String | Да | Уникальный идентификатор | Генерируется автоматически (cuid) |
| `name` | String | Да | Уникальное имя роли | Уникально в системе, регистрозависимое; для системных ролей — неизменяемое |
| `description` | String? | Нет | Текстовое описание назначения роли | Опциональное, до 500 символов |
| `is_system` | Boolean | Да | Признак системной роли | По умолчанию `false`. `true` защищает роль от удаления и переименования |
| `created_at` | DateTime | Да | Дата создания роли | Генерируется автоматически |
| `updated_at` | DateTime | Да | Дата последнего обновления | Обновляется при каждой записи |

## Связи

| Сущность | Тип связи | Описание |
|----------|-----------|----------|
| User | has_many через `user_roles` | Роль может быть назначена нескольким пользователям (M:N) |
| Page | has_many через `role_pages` | Роли назначаются страницы, к которым предоставляется доступ (M:N) |
| ApiEndpoint | has_many через `role_api_endpoints` | Роли назначаются API endpoints, к которым предоставляется доступ (M:N) |

## Индексы

| Поля | Тип | Описание |
|------|-----|----------|
| `name` | unique | Уникальное имя роли |

## Бизнес-инварианты

- `name` уникально в системе
- При `is_system = true` роль нельзя удалить или переименовать (защита на уровне сервиса)
- Роль `SUPER_ADMIN` (`is_system = true`) предоставляет доступ ко всем страницам через runtime-правило в коде проверки доступа, а не через `role_pages`
- Удаление роли каскадно удаляет все записи в `user_roles` и `role_pages`, связанные с этой ролью
- Перед удалением несистемной роли сервис обязан проверить, не является ли роль последней, обеспечивающей доступ хотя бы одному пользователю к критичным разделам (предупреждение в UI)
- Нельзя удалить роль, если это последняя роль `SUPER_ADMIN` хотя бы у одного пользователя

## Seed данные (при миграции с enum `Role`)

| name | description | is_system |
|------|-------------|-----------|
| `SUPER_ADMIN` | Супер-администратор. Полный доступ ко всем страницам. | true |
| `ADMIN` | Администратор. Настраиваемая роль. | true |
| `MEMBER` | Член СНТ. Настраиваемая роль. | true |
| `GUEST` | Гость. Настраиваемая роль. | true |

> При миграции существующее поле `users.role` (enum GUEST/MEMBER/ADMIN) переносится в `user_roles`: для каждого пользователя создаётся запись, связывающая его с соответствующей системной ролью. Поле `users.role` после этого удаляется.
