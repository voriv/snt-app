## Архитектурное решение: sidebar — статика vs Page (RBAC)

### Контекст

US-NAV-05 (sidebar) и US-NAV-02 (navbar) требуют отображения навигационных пунктов меню. Возникает вопрос: откуда брать список пунктов меню?

### Варианты

#### Вариант A: Статическая конфигурация в коде

Пункты меню захардкожены в TypeScript-массиве (конфиг), ролевой фильтр применяется на клиенте.

**Плюсы:**
- Простая реализация, быстрая разработка
- Нет дополнительных API-запросов
- Данные ролей уже в сессии

**Минусы:**
- Требует пересборки при добавлении/удалении страниц
- Нет динамического управления через админ-UI
- Дублирование данных (пункты меню ≠ страницы RBAC)

#### Вариант B: Сущность Page (RBAC) из БД

Использовать существующую сущность `Page` как источник данных для навигации. Page содержит: `path`, `title`, `group_name`, `sort_order`, `is_active`, `access_type`. Ролевой доступ через `role_pages`.

**Плюсы:**
- **Единый источник данных** — те же страницы, что защищаются RBAC, отображаются в меню
- **Динамическое управление** — изменение меню через админ-UI (без пересборки)
- **Консистентность** — `is_active=false` скрывает страницу из меню и блокирует доступ
- **Группировка и сортировка** — `group_name` и `sort_order` уже поддерживают структуру меню
- **Ролевой доступ** — `role_pages` определяет, какие страницы видит каждая роль

**Минусы:**
- Требует API-запроса для загрузки пунктов меню при инициализации (1 запрос)
- Иконки пунктов меню — клиентский маппинг (статический)

### Принятое решение: ✅ Вариант B (Page из БД) + клиентский маппинг иконок

**Обоснование:**

1. **Сущность Page уже существует** и содержит все поля, необходимые для навигации:
   - `path` — URL-путь пункта меню
   - `title` — текст пункта меню
   - `group_name` — группировка пунктов
   - `sort_order` — порядок в меню
   - `is_active` — видимость в меню
   - `access_type` + `role_pages` — ролевой доступ

2. **Консистентность между RBAC и навигацией** критична: страница, добавленная в RBAC, должна автоматически появиться в меню (для назначенных ролей).

3. **Иконки реализуются через клиентский маппинг** (статическая функция `getIconByPath(path)`), так как:
   - Иконки — UI-деталь, не бизнес-данные
   - Можно использовать компоненты Lucide React по имени
   - Нет необходимости хранить имена иконок в БД

4. **API-запрос один** при инициализации дашборда (загрузка страниц + ролевой фильтр).

### Структура данных для навигации

```typescript
// Тип пункта навигации
interface NavItem {
  path: string;        // Page.path
  title: string;       // Page.title
  groupName: string;   // Page.groupName
  sortOrder: number;   // Page.sortOrder
  icon: string;        // клиентский маппинг: getIconByPath(path)
}

// Источник данных: GET /api/v1/pages?active=true
// Фильтр: role_pages для ролей пользователя (из сессии)
```

### Маппинг иконок (клиентский, статический)

```typescript
// src/lib/nav-icons.ts
const pathIconMap: Record<string, string> = {
  '/dashboard': 'layout-dashboard',
  '/dashboard/plots': 'map',
  '/dashboard/users': 'users',
  '/dashboard/comms': 'message-square',
  '/dashboard/documents': 'file-text',
  '/dashboard/payments': 'credit-card',
  '/dashboard/roles': 'shield',
  '/profile': 'user',
};

function getIconByPath(path: string): string {
  return pathIconMap[path] ?? 'circle';
}
```

## Влияние на слои архитектуры

### Модель данных
- **Без изменений.** Используются существующие сущности: User, Role, Page, RolePage.

### Repository
- **Без изменений.** Существующие репозитории достаточно для загрузки страниц.

### Service
- **Опционально.** Новый метод `getMenuItemsByRoles(roles: string[]): NavItem[]` — комбинация Page + RolePage данных с клиентским маппингом иконок.

### API
- **Опционально.** Эндпоинт `GET /api/v1/pages/menu` — получение активных страниц с учётом ролей пользователя. Может использовать существующий `GET /api/v1/pages` с ролевым фильтром.

| `/dashboard/payments` | Платежи | Основное | 50 | role |

> **Примечание:** Добавление записей в seed — задача этапа `plan` (B-009 → plan), так как требует решения по конкретным маршрутам и группам.
